# Candidate and specification contract

Each item has key, kind, title, summary, content_markdown, evidence, assessment, tests and gaps. kind is module, feature, requirement_document, requirement or architecture. Documents may carry artifact_type from dossier-plan.md. Module has no parent; feature and requirement_document require module_key. For every included capability, each linked requirement must carry the capability's module_key and feature_key; document_key is an optional same-module document association. Omitted feature_key is supported by the schema for compatibility or unfinished drafts, not for a complete included capability. Architecture has no parent and requires diagram_source (Mermaid). Referenced parents must be candidates; reviewers may bind them to existing entities.

Evidence paths/hashes come from source.files and real 1-based line ranges. Read the cited range to confirm it supports the precise claim; a valid hash and in-bounds range alone are insufficient. assessment is observed_in_code, documented, inferred, proposed or unknown. Reporting what a material states is documented even if it describes code; adopting a proposed rule still requires decision evidence. Code observations prove implementation behavior, not the business owner's intent. Follow [scope.md](scope.md) to distinguish current observations, intended rules and proposals, including known defects. tests have path, name, status and optional note; paths must be captured files. gaps retain unknown behavior and verification not performed.

For each structured requirement, write the following fields. A requirement document may also carry them as supplemental material, but does not replace the feature-linked requirement candidates in the capability inventory:
- acceptance_criteria: [{id,text}]. IDs are stable within the item; each text describes an observable outcome under stated conditions.
- specification: {actor,trigger,preconditions:[],main_flow:[],exceptions:[{condition,handling}],business_rules:[],state_changes:[],data_contracts:[]}.
- verification_plan: [{ac_id,method:"manual"|"automated",preconditions,steps:[],expected}]. Link ac_id to a real acceptance ID; distinguish planned checks from actual tests.

Write AC text in natural language. Each AC needs a linked plan whose preconditions, concrete steps and expected result make its scenario testable; those fields carry the condition/action/outcome without requiring the writer to repeat fixed Given/When/Then or 当/预期 wording. Empty text, placeholder steps and an unlinked plan do not establish a testable scenario. If meaningful structured fields still receive a prose-keyword failure, record the rule ID and the existing field evidence for evaluator correction rather than adding filler.

Make each verification plan reproducible from its own stated baseline. Specify relevant actor/permissions, seeded records, initial state, clock/time zone and external-service outcome. Reset state between compared runs or explicitly declare a sequential scenario and the state it inherits. For a retry or repeated request, distinguish the same request identity from a new request. Assert both the visible result and material preserved/changed state; avoid tests whose outcome depends on leftovers from an earlier case. Use controlled conditions only where they influence the result, without inventing implementation details.

For an asynchronous outcome, distinguish request acceptance or publication from processing completion. Include the required processing/recovery step and observable condition for reaching the asserted terminal result; record an unavailable mechanism or waiting limit as unresolved rather than inventing a worker, timeout or completed run.

Trace a complete successful scenario, denied permission and meaningful failure/recovery path. Explain unchanged states as explicitly as changed states when material. Include identifiers/field constraints, errors, retries and transaction/consistency boundaries where supported. If a dimension is inapplicable, state why in its entry; do not manufacture controls.

Acceptance example (adapt to real evidence): Given an editor and revision 3, when saving content based on revision 2, the save is rejected and revision 3 remains unchanged. Verification specifies actor/setup, the exact operation, and how rejection plus preserved state is observed. This is testable without pretending a test was executed.

Use dossier templates for shared context, architecture, API/data, security, operations and testing strategy. Cross-link stable requirement/capability IDs and their source evidence. Reconcile repeated rules across overview prose, structured specifications, ACs, plans, API/data details and runbooks: rejection versus ignored input, limits, permissions, and transaction outcomes must agree or explicitly name a real variation. Do not keep mutually exclusive outcomes as interchangeable acceptable answers to hide a missing decision.

Requirements need depth, not repeated boilerplate. Source-only projects can provide planned verification; no fabricated test file is needed. NFR targets require units, conditions and verification approach; business targets and measurements that are unknown remain explicit unknowns. Record relevant standard mappings only with an identified standard/version and a specific applicable criterion; using a template or passing local rules does not establish conformity or certification.
