# 从源码逆向重建项目资料

目标读者是接手项目的产品、工程、设计和测试成员。最终应能从一个用户操作追到实现条件、原型状态和可验证结果。先读 [交付与评审约定](references/artifacts.md)。已有历史资料用来核对变化；新结论以指定版本的源码为依据。

1. **固定输入。** 记录项目目的、操作者给出的背景、仓库身份、提交或工作区草稿、覆盖的目录与排除项。采用已有固定快照；普通 Git 项目可用指定提交的独立 checkout。纳入未提交源码时，先冻结选定文件的字节。根据固定副本生成或复用包含相对路径与 SHA-256 的清单。把作者提供的产品意图、从架构推得的假设和在代码中观察到的行为分开。
2. **先设计全貌。** 从可见页面、命令、路由、后台作业及外部适配器清点入口，说明用户、核心业务对象、系统边界、模块职责和预期功能。对照入口逐一分配主责模块；保留未覆盖入口与原因。模块围绕用户目的和状态所有者划分。让作者用固定源码修正这份初始设计。小范围项目可以用同一人分两遍完成。
3. **分模块取证。** 有 UA、CodeGraph 或等价索引时，先以模块地图和调用关系找起点，再复核对应源码、迁移、配置及测试。无图工具时，从入口跟随实际调用、引用和数据写入，并记录导航方式。大项目给独立作者相同的背景、版本、交付约定和互不重叠的模块；每个作者回报查询、关键发现、跨模块争议和未决点。按角色和用户动作写功能，给稳定编号、条件、正常结果、拒绝/冲突/重试行为和可观察的验收条件。对没有实现依据的设计标注“拟议”。
4. **综合交付。** 产品背景和系统架构说明边界与模块；模块说明细化功能；原型让读者操作主要用户旅程的正常与异常分支；数据、接口、权限、验收、部署恢复分别交代其约束。多个产物沿用相同功能编号。纯库或无界面服务可以用真实 API/CLI 交互样例代替屏幕原型，并在交付范围写清原因。商务承诺、客户 SLA、合规结论和签字验收须有独立来源。
5. **交叉核验。** 独立审阅者从重要状态转换取一条正常操作、一条被拒操作，核查源码条件和副作用，实际打开原型并操作分支。反向从 UI/命令/服务目录检查遗漏。对照文档、原型、验收描述是否一致，保留阻断问题、修正和未覆盖点。测试源码、运行结果、组织决策分别留证。按 [证据核验与机械校验](references/verification.md) 保留原始引用、检查命题与分支；取证或评审受阻时，从固定原文恢复准确摘要。
6. **交付与复跑。** 为修订保存来源版本、资料位置、覆盖清单、检查结果与审核状态。发布到资料库时使用所在平台的原生修订与权限；回读标题、正文、原型及版本。复跑先按来源指纹和模块/旅程依赖确定受影响产物，保留已有 ID 和与本次无关的编辑；发生并发冲突时重读后再更新。只在任务明确包含清理时处理旧数据。

在 TeamSynergy 中交付或因流程受阻而修订本技能时，读[平台交付与技能迭代](references/team-synergy.md)。可复用平台固定的分析运行，使用 UA 导航、CodeGraph 定位，再用原文证实。需要结构化 intake 候选时采用宿主的 spec-production 流程及其 schema。
