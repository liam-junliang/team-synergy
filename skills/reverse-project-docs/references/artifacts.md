# 交付与评审约定

先写出接手者真正需要完成的工作，例如“接手一项已开始的工作后，怎样判断当前版本还能继续”。为这个问题同时准备操作原型、状态规则和验收依据。整项目交付可按下表组织；交付范围按实际系统说明。

| 读者与产物 | 需要回答的问题 | 交付前如何检验 |
| --- | --- | --- |
| 负责人 · 产品背景及系统设计 | 谁使用，目标是什么，边界和主要子系统是什么，哪个模块对哪类事实负责？ | 每个关键入口在覆盖清单中有归属。职责存在重叠时明确交接方式。 |
| 产品与工程 · 模块需求 | 角色、前提、动作、成功后的持久记录与可见结果是什么？状态变化后之前的操作还能执行吗？ | 每个功能有稳定 ID、条件、结果、例外及源码或明确的未知项。重要权限与版本约束在原始判断处核实。 |
| 设计与业务 · 原型与交互说明 | 用户从哪里开始，能看到哪些字段、做什么，出错怎样恢复？ | 用实际可交互的页面或协议样例。走通正常与关键异常场景、角色差异及退出/恢复；核对键盘、小屏和可读反馈。标注示例数据与未实现设计。 |
| 架构与集成 · 组件、数据与接口 | 调用方、身份、对象主键/修订、请求响应、副作用和可重试条件是什么？ | 以真实入口跟到状态所有者，区分同一事务的写入、异步任务和外部回执。不要用静态调用图推定运行顺序。 |
| QA · 验收与非功能 | 用什么角色/初始数据，执行哪一步，观察哪个字段或副作用？失败、重复请求、越权、过期版本怎样判定？ | 写出具体用例 ID 并与需求、原型状态、源码断言互查。列出实际环境、未运行的场景及待定义的指标。 |
| 运维与治理 · 运行交付 | 部署、依赖、权限变动、监控、降级、恢复如何影响业务可用性？ | 给可核对的配置与验证方法；已有演练的证据需能定位到版本与环境。 |

作者交接时为关键功能标注：产品意图的来源；固定源码的路径和行号；用例在测试里定义了哪些断言；哪部分需要环境或负责人确认。跨模块的“有关联”只能引导阅读。把 A 写成 B 的执行门槛，必须找到 B 路径中实际检查 A 的位置。

评审从接手者视角抽查四件事：能找到入口、能解释一个拒绝分支、能指出事实记录的位置、能说明何种证据才算交付。问题按“影响哪个功能／当前结论／源码或操作证据／修订后结果”记载。高影响分支没有证据时，保留为未决项。
## 工具组合与预览环境

使用 codebase-graph-prd-rules 时，整项目清点对应 codebase-graph-business-rules；确定模块后再参考 codebase-graph-module-rules 查角色、规则、顺序、边界和反例。记录实际可用的分析器、输入版本与产物。UA 的结构、CodeGraph 的源码导航和规则分析方法各有用途；使用其中之一并不等于执行了另外两种工具。

HTML 原型要在交付宿主中实点。例如 iframe 的 srcdoc 中，相对片段链接可能解析为宿主页面；本地单文件测试不能发现这种错误。至少验证正常和受阻分支、键盘操作、窄屏、目标状态可见性、实际预览安全策略以及是否意外离开原型。保留操作记录和截图；说明哪些数据是夹具，哪些行为经过真实业务测试。
