# 在 TeamSynergy 中交付和改进技能

## 把分析模块对应到项目资料

逆向分析可以按身份、权限、资料库等细分领域。项目负责人已在平台设置的功能模块和 Feature 可能采用另一种划分。发布资料前，用 `tsp module list`、`tsp feature list` 读取当前项目清单。在模块资料中记录分析模块 ID、对应的平台模块或 Feature 编码，以及匹配理由。多对一和跨模块关系可以保留。找不到对应项时标为待归属，附调整建议。创建、迁移平台业务模块属于单独的项目变更。

例如分析出了 13 个领域，项目页登记了 5 个模块，交付时分别报告这两个数量，附对应表。编写一篇领域说明后，从文档库回读正文和修订号；若任务还要求变更模块或推进需求，另从相应业务入口核对状态。仅凭目录名、文档数或一张截图不能确认已录入业务对象。

按资料用途选择交付入口。系统设计、模块需求、术语、长期维护的测试策略等归文档库或对应业务页面。一次验收的执行结果、运行日志和截图归测试执行或缺陷。源码快照、构建包以任务产物 URI 和内容指纹提交。文档需要举证时链接已保存的原件；交付验收时分别从这几个入口回读。

## 遇到流程卡点

先记录发生在取证、推导、原型操作、评审、发布还是回读。留下受测技能源和固定版本、期望与实际、可复现的最小输入和脱敏证据。把解除阻塞的办法用同一输入再跑一次。技能说明不足、校验脚本遗漏、平台工具缺陷可以同时存在，分别定位并关联记录。

取证选择、摘要或事实评审受阻时，按[语义证据与受阻恢复](verification.md#语义证据与受阻恢复)核对原始引用、陈述范围和证据强度。用固定原文确认真实的信息丢失，再修复对应环节；把已恢复的准确事实、仍未证实的事项和需纠正的陈述分别交回流程，不能用形式上完整的占位条目绕过卡点。

- **技能说明或脚本需要改**时，在 TeamSynergy 仓库的 `skills/reverse-project-docs/` 修改能消除歧义的最小部分。用旧例复现，再用改后的技能从干净工作区执行；涉及通用规则时，再用一个适用范围不同的例子检查是否误伤。将修订、复跑结果和对应项目问题关联。
- **工作台或工具有缺陷**时，走项目缺陷和修复验证流程。例如果然无法滚动，修复并回测工作台；如果原型在宿主中表现与单文件预览不同，保存这一差异后补入技能的宿主验证步骤。对单次服务错误先确认原因，再判断是否值得修改公共流程。
- **发布新版本**时，更新入口中的技能版本，将参考资料和脚本作为同一包发布。核对平台分发的版本和实际文件，分别从干净成员工作区和已有固定版本的 Run 回读。让项目显式选择升级，保留现有 Run 的证据和可复跑版本。

成员从项目采用的技能清单读取固定版本。CLI 可用 `tsp skill list --project <项目编码>` 查看采用情况，用 `tsp skill sync --project <项目编码> --check` 预览差异，再用同一命令去掉 `--check` 同步。Run 使用 `tsp skill sync --run <Run编码>`。记录实际采用的修订与内容指纹，便于下一位成员复验。维护时改仓库内的发布源，本机 Codex、DSH 或 OpenCode 的安装副本只用于执行。
