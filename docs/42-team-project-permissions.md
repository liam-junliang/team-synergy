# 团队、项目权限与所有权转移设计

- 状态：角色、默认访问、外部协作、所有权转移与恢复、账号注销已实现；历史多 Owner 数据保留待确认状态，按 §7 完成受审计的迁移。
- 日期：2026-10-16
- 范围：团队与项目角色、默认访问规则、外部协作者、所有权转移、账号注销及存量迁移。
- 已明确的产品要求：团队与项目角色分开；负责人唯一；注销前转移责任；项目成员可以不是团队成员。
- 新项目默认 `team_read`，创建时可明确选择；旧项目迁移为 `private`。接收团队或项目所有权的账号必须是所属团队的有效正式成员。不会自动扩展旧项目授权或将外部用户加入团队。

## 1. 身份与权限分开

| 概念 | 含义 | 能否变更 |
| --- | --- | --- |
| 创建者 | 最初创建团队或项目的历史账号 | 不随转移改变；无可靠记录时显示“历史未记录” |
| 负责人（Owner） | 当前承担管理责任的唯一账号 | 只能通过所有权转移或受审计的恢复流程变更 |
| 管理员（Admin） | 可处理日常管理的账号 | 可以有多名，由对应范围的负责人任免 |
| 成员 / 观看者 | 协作或只读权限 | 按所在范围授权 |
| 外部协作者 | 有项目权限，但不是项目所属团队的成员 | 是身份标识，不是第五种项目角色 |

创建团队或项目时，创建者同时成为第一任负责人。转移后，新的负责人不能被标成创建者。界面主要展示“负责人”，另在详情显示创建者；英文统一为 Owner / Admin / Member / Viewer。

新建及完成迁移的团队、项目恰好有一个负责人身份。历史多 Owner 对象在明确选择前显示“负责人待确认”，不能通过普通角色编辑增加 Owner。账号被紧急禁用时，保留其所有权记录并进入恢复流程，不能为了维持“有效负责人”而禁止紧急禁用。

## 2. 两套角色与权限矩阵

### 2.1 团队

| 能力 | 团队负责人 | 团队管理员 | 团队成员 |
| --- | --- | --- | --- |
| 查看团队基本信息与成员 | 是 | 是 | 是 |
| 修改团队资料 | 是 | 是 | 否 |
| 创建团队内项目 | 是 | 是 | 否 |
| 添加、移出普通团队成员 | 是 | 是 | 否 |
| 任免、移出团队管理员 | 是 | 否 | 否 |
| 查看团队全部项目的名称、状态和负责人等治理信息 | 是 | 是 | 仅有权访问的项目 |
| 读取项目正文或管理项目成员 | 按项目有效权限 | 按项目有效权限 | 按项目有效权限 |
| 转移团队所有权 | 是 | 否 | 否 |
| 解散团队 | 仅负责人，独立流程 | 否 | 否 |

团队管理员不能修改同级管理员或负责人，不能通过团队移出功能绕过项目负责人保护。解散团队前必须逐项处理项目，不能顺带删除项目资料；第一阶段不新增永久删除能力。

### 2.2 项目

| 能力 | 项目负责人 | 项目管理员 | 项目成员 | 观看者 |
| --- | --- | --- | --- | --- |
| 阅读资料、历史、计划和任务，搜索与下载 | 是 | 是 | 是 | 是 |
| 参与需求讨论、创建协作资料 | 是 | 是 | 是 | 否 |
| 编辑资料、提交任务成果 | 是 | 是 | 在对象与任务授权范围内 | 否 |
| 领取并执行任务、启动 Agent Run | 遵守任务身份约束 | 遵守任务身份约束 | 遵守任务身份约束 | 否 |
| 维护项目资料、仓库、模块、计划，分派任务及正式审批 | 是 | 是 | 仅既有明确委派的操作 | 否 |
| 添加、调整和移出项目成员/观看者，包括外部协作者 | 是 | 是 | 否 | 否 |
| 任免或移出项目管理员 | 是 | 否 | 否 | 否 |
| 修改团队默认访问方式 | 是 | 否 | 否 | 否 |
| 项目归档、恢复及所有权转移 | 是 | 否 | 否 | 否 |

“项目成员”不叫“团队成员”，避免混淆。外部协作者也可被明确授予 Admin、Member、Viewer；外部管理员与内部管理员遵守同样的项目权限限制，均没有团队管理权。

负责人和管理员也不能绕过版本冲突、项目归档、任务状态机、运行身份或审批约束。观看者不能写入评论、投票、编辑、上传、领取或提交任务；历史作者身份不构成绕过只读角色的理由。

## 3. 默认访问方式与外部协作

无需将所有团队成员复制到每一个项目。项目设置提供三个清楚的选项：

| 模式 | 代码 | 没有单独配置角色的团队成员 | 外部用户 |
| --- | --- | --- | --- |
| 仅指定成员 | `private` | 无权限 | 仅显式授权者可访问 |
| 团队可读，指定成员协作 | `team_read` | Viewer | 仅显式授权者可访问 |
| 团队共同协作 | `team_write` | Member | 仅显式授权者可访问 |

新项目默认 `team_read`，创建页明确展示其影响；现有项目一律先保留 `private`，不因升级扩大阅读范围。

**有效权限按以下顺序计算，不是取各来源中的最高权限：**

1. 账号无效或凭据失效：无权限。
2. 当前项目负责人：Owner。
3. 存在有效的显式项目角色：使用该角色，包括比默认规则更低的 Viewer。
4. 没有显式角色且当前属于项目团队：使用访问模式对应的默认角色。
5. 其他情况：无权限。

例如，team_write 项目中单独配置的 Viewer 仍然只读。团队 Admin 不会自动变成项目 Admin。外部用户在 team_read 项目也不能凭项目链接获得访问权。

外部成员仅获得指定项目的数据权限，不因此获得团队成员资格、团队成员目录或其他项目的访问权。添加外部用户时明确提示范围；不自动将其加入团队。

### 3.1 撤销与默认权限恢复

- 对共享项目内的团队成员，移除显式角色意味着“恢复团队默认权限”，不等于禁止访问；操作前显示变更后的角色。
- 特别是 team_write 下撤销显式 Viewer，会恢复为 Member。界面不能把这个操作写成“移出项目”。
- 外部成员没有团队默认权限，撤销其显式授权才是真正的“移出项目”。
- 第一阶段不叠加按人拒绝名单。需要排除个别团队成员的项目使用 private，并显式授权参与者。
- 切换项目访问模式展示新增可读/可写人数、失去写权限或全部访问的人数和保留的显式例外，留下审计；私人项目不能被普通成员或团队管理员单方面开放。
- 从 team_write 改为 team_read/private 时，受影响的继承成员必须先交接未完成任务及准备中、活动或暂停的 Run。检查与策略更新在同一事务和项目锁内完成；未交接则整次更新失败。负责人和仍有显式协作授权的成员不因默认规则改变而降权。

### 3.2 离开团队后的权限

- 团队规则产生的继承访问立即失效。
- 正常移出团队时，先展示项目权限、负责人和未完成工作影响清单，再撤销该人在本团队各项目的显式授权，防止离职后无意保留访问。
- 如仍需外部合作，由项目负责人在移出后重新授予指定项目角色，明确记录为外部协作授权；本次不提供团队管理员一键保留项目授权的旁路。
- 原本就是外部协作者的人不受无关团队成员操作影响。
- 仍为团队负责人或本团队任一项目负责人的人，必须先完成对应转移。再次加入团队时，已撤销的旧授权不能自行复活；经项目负责人确认且持续有效的外部显式授权继续保留，只更新内部/外部身份标识。

## 4. 转移、注销与紧急恢复

### 4.1 正常转移

1. 当前负责人发起转移，选择接收人；创建有效期为七天的转移请求。同一团队或项目同时只能有一个待处理请求。
2. 接收人明确接受后生效。未接受、过期、被取消的请求不改变当前权限。
3. 团队与项目的新负责人必须是该团队的有效正式成员，且不处于待注销状态。外部协作者接任项目前，先加入团队。
4. 项目接收人可以原本仅有团队默认访问；接受时建立显式管理关系，所有权不再依赖默认访问模式。
5. 接受时在一个事务内再次验证双方身份、当前负责人、目标团队资格、请求状态与有效期；按用户、团队、项目、转移记录顺序加锁，更新唯一负责人、成员角色和审计。重复接受只能成功一次。
6. 原负责人默认保留为对应范围的 Admin；后续退出或注销另行处理。不能通过普通角色下拉框升为 Owner，也不能直接降级/移除当前 Owner。

团队与项目分开转移。转移团队不自动转移团队下所有项目；注销账号则检查该账号在所有团队中的全部所有权。归档项目仍需要负责人，允许治理类转移，不必先解冻正文。

### 4.2 账号注销

“创建过”不阻止注销，“目前仍负责”才需要转移：

- 检查页列出全部仍负责的团队和项目，含归档项目，每项提供转移状态。
- 单纯的普通成员、观看者和历史作者不需要为每个项目转移所有权。
- 正式进入注销流程后，不允许新建团队/项目或接受新的所有权；仍可完成必要的转移与工作交接。
- 未完成全部转移时不能最终注销。没有接收人则继续保留账号，或走明确的团队/项目关闭流程，不能自动找一个成员接任。
- 最终注销在事务内重新检查所有权，和所有权写入使用一致的账号锁与状态校验，防止“检查后又获得一个项目”的竞争。
- 待办任务、进行中的 Run、个人设备绑定另列交接清单，不随项目所有权一起变成新负责人的任务。活动 Run 必须终止/交接，待办必须重新分派或回到待分配状态。
- 注销撤销 Web 会话、CLI/设备凭据、绑定 Token 和 Run 写入资格；服务端后续请求不能依赖旧缓存继续获得权限。
- 保留非登录历史身份以承接文档作者、版本和审计引用，界面可标识“已注销用户”；不把过去的作者改成接收人。个人信息清理策略单独定义。
- 平台管理员不能同时注销到无人管理的状态；最终注销保留至少一名有效平台管理员。

### 4.3 紧急禁用不等同于注销

被盗或违规账号应立即禁用并撤销访问，不能等待接收人同意转移。此时原唯一负责人记录暂时保留，空间进入“负责人不可用”的治理状态。

团队负责人可以通过独立且可审计的恢复操作，处理本团队中负责人已注销/禁用的项目；团队负责人本身不可用时由平台管理员处理。必须记录操作者、原因、原/新负责人和时间，不通过修改成员角色假装正常转移。恢复入口不自动赋予团队管理员日常读取私人项目正文的能力。

恢复流程仍须在事务内验证新负责人的账号状态与团队资格，并由接收人接受；它只免除失效原负责人的发起动作，不绕过接收资格和唯一所有权约束。

如果旧多 Owner 数据中的候选负责人全部不可用，平台管理员可以先从原有且属于该团队的 Owner 中明确一个责任身份，再走恢复流程。该确认不会激活账号，也不能把任意新用户直接提升为负责人。接收恢复请求时会再次检查原负责人仍不可用、发起人仍有恢复权限。

## 5. 页面与 CLI

- 团队成员面板展示“负责人 / 管理员 / 成员”，不再提供“授予 Owner”。唯一负责人有独立“转移负责人”入口。
- 项目设置分别展示“访问方式”和“成员与权限”。成员显示有效角色、内部/外部身份、权限来源（负责人 / 单独授权 / 团队规则）。
- 继承访问者按团队名单计算，搜索、分页和统计不能只读取显式成员表；任务分派候选人同样按有效协作权限计算。
- 没有正式团队成员资格的项目用户展示“外部协作者”；团队信息只能提供理解项目归属所需的最少名称，不暴露团队名册。
- 项目切换器、项目列表、文档检索、CLI 列表使用相同的可见性计算；浏览器隐藏按钮不是权限边界。
- CLI 继续沿用 `tsp`；团队与项目的成员命令使用不同角色类型。转移拆为发起、查看、接受、取消；普通成员修改命令不能写入 owner。
- 机器结果返回 `effective_role`、`access_source`、`is_external` 与 `capabilities`，并使用稳定错误码。Agent 权限不得超过所属用户的实时权限；Run 的任务范围限制继续生效。

### 5.1 团队与项目入口（已实现）

- 默认“全部项目”独立读取当前用户有权访问的项目，不要求先选择或加入团队。
- 左侧“我的团队”只列正式加入的团队；“外部协作”列出用户有项目授权、但没有所属团队成员身份的项目。点击我的团队只筛选该团队内已授权的项目。
- 项目卡片和顶部项目切换器显示所属团队名称、当前项目角色与外部协作标记；外部团队名称仅是项目归属说明，不提供团队管理、团队名册、其他项目或团队统计入口。
- 没有团队但有外部项目时，仍可直接打开项目。项目为空时提示等待授权，不要求先创建团队。团队请求失败不能阻塞项目入口；身份无法确认时不猜测为外部，可从全部项目访问。
- 项目操作依项目角色控制；团队管理及新建项目只在选择实际加入的团队后展示，继续按现有权限校验。项目排序仅在单个团队视图提供，避免把跨团队顺序写成团队内顺序。
- `/projects` 按有效权限返回项目，包含 `team_name`、`is_external`、`effective_role`、`access_source`、`member_policy` 与 `capabilities`。不因显示团队名称而授予团队权限，也不把外部用户自动加入团队。
- 团队治理列表仅向团队 Owner/Admin 提供全部项目的名称、状态、负责人及 `can_access`。没有项目访问权限时不提供正文链接、摘要或成员名单；普通团队成员只能看到自己可访问项目的数量。

### 5.2 CLI 操作

所有命令使用本机 `tsp auth login` 登录身份，响应采用 JSON envelope。项目命令可显式传 `--project`，也可以使用 `tsp project bind` 的当前目录绑定。普通授权只能设置 `admin/member/viewer`；团队没有 Viewer。

```sh
# 查看正式团队成员、修改普通团队角色、预览移出影响
tsp team members <team_code>
tsp team role <team_code> <user_code> --role admin
tsp team remove <team_code> <user_code> --preview
tsp team remove <team_code> <user_code>

# 项目成员包含团队继承访问者；显式角色可覆盖默认权限
tsp project members <project_code>
tsp project member add <user_code> --project <project_code> --role viewer
tsp project member role <user_code> --project <project_code> --role member
tsp project member remove <user_code> --project <project_code>

# 先预览新增/失去访问的人，再由项目负责人设置访问模式
tsp project policy team_write --project <project_code> --preview
tsp project policy team_write --project <project_code>
tsp project policy --project <project_code>

# 发起后由接收人使用自己的登录身份接受；项目与团队分别转移
tsp ownership transfer project <project_code> <user_code>
tsp ownership transfer team <team_code> <user_code>
tsp ownership list
tsp ownership accept <transfer_code>
tsp ownership cancel <transfer_code>

# 失效负责人恢复需要治理权限、原因和接收人接受
tsp ownership recover project <project_code> <user_code> --reason "原负责人账号已禁用"
# 历史多 Owner 确认只能选择现有 Owner，不是普通授权入口
tsp ownership resolve project <project_code> <existing_owner_code>

# 注销前处理全部责任，包含归档项目和进行中的工作
tsp account closure status
tsp account closure begin
tsp account closure cancel
tsp account closure complete --confirm
```

`project member remove` 返回变更后的 `effective_role`、`access_source`。在共享项目里撤销显式 Viewer 可能恢复为 Member，调用者应据此解释结果。`ownership list` 只返回与登录用户有关的转移；管理员不能借此读取全平台转移记录。注销完成后当前 Web/CLI 设备凭据同时失效，需使用其他账号重新登录。

## 6. 存储与授权实现

- 团队、项目分别记录 `created_by` 和唯一 `owner_principal_id`。新建对象必须写入；旧数据无法可靠还原创建者时保留 null 和来源说明。
- 团队成员存储角色为 admin/member；项目显式成员为 admin/member/viewer。Owner 从对象的唯一负责人字段派生，不在两处独立保存所有权。负责人本身保留显式管理成员关系。
- 项目新增 `member_policy`；团队默认访问实时计算，不批量生成成员行。团队/角色/模式改变要使授权缓存及时失效。
- 负责人身份、成员关系、转移请求和审计在同一事务内变更；所有权字段、合法角色及对象归属以数据库约束配合事务保证。接受转移与注销使用一致的用户锁，转移额外锁定团队、项目和请求记录并复核状态。
- 统一服务端的 `resolveProjectAccess` 与能力检查，覆盖 Web、CLI、普通用户和 Run 身份；业务用例随后继续验证对象作者权限、状态机与版本。
- 对每次写操作先检查有效角色的写能力，再检查“作者/负责人可编辑”等对象规则；降为 Viewer 的历史作者也必须只读。
- 无访问权者不能通过任务列表、图谱、ID 直达、历史版本、附件、搜索片段或分享链接绕过项目范围。调用者身份必须取自认证上下文，不能由查询参数任意指定。

## 7. 当前实现与保守迁移

当前实现入口：

- [contracts/schemas.ts](../packages/contracts/src/schemas.ts)：独立的 TeamRole、MemberRole 和 ProjectMemberPolicy。
- [project-access.ts](../packages/application/src/project-access.ts)：统一计算有效访问和项目能力；禁用、注销账号无访问权限。
- [team-use-cases.ts](../packages/application/src/team-use-cases.ts)、[member-use-cases.ts](../packages/application/src/member-use-cases.ts)：成员层级、继承权限列表、团队移出影响与事务保护。
- [project-policy-use-cases.ts](../packages/application/src/project-policy-use-cases.ts)：仅项目负责人可预览或修改默认访问方式。
- [ownership-use-cases.ts](../packages/application/src/ownership-use-cases.ts)：正常转移、恢复、历史确认和账号注销；紧急禁用仍由用户管理用例处理。
- [0034_permissions_ownership.sql](../packages/persistence/drizzle/0034_permissions_ownership.sql)：新增创建者、唯一负责人、项目默认访问、转移记录和独立项目排序表。
- [permissions.ts](../apps/cli/src/permissions.ts)：CLI 成员权限、访问方式、所有权与注销入口。

存量迁移规则：

1. 先导出每个团队/项目的 Owner、成员、账号状态、创建审计、团队归属以及外部成员清单，产生可审查的迁移计划。
2. 只有一个现有 Owner 的，迁移保留为负责人并将存储成员角色转为 Admin。多个 Owner 暂时保留兼容访问，标记“负责人待确认”，必须通过 `ownership resolve` 明确选择负责人，其他 Owner 转为 Admin；不能把第一个成员、最早成员或历史创建者自动当作当前负责人。新的普通授权接口始终禁止写入 owner。
3. 创建者仅依据可靠的创建审计回填；缺失则如实标记。新增管理员保留原 Owner 的日常治理能力，所有权转移等少数专属能力明确收回。
4. 全部旧项目初始为 private，普通成员保留显式项目授权。团队外的普通协作者继续有效，不强制加入团队。
5. 旧项目的唯一 Owner 若是团队外用户，列为单独决策项：明确同意加入团队后继续负责，或选定团队内接收人。迁移不得静默扩大该用户的团队访问，也不得随意撤销所有权。
6. 未完成负责人确认的旧对象不能直接开启默认共享或发起转移；先处理负责人归属，再开放这些治理操作。旧外部 Owner 不会被静默加入团队，需先明确团队归属或接收人。
7. 数据迁移不重写文档、版本作者、项目编码、任务历史或审计；记录映射与权限变化以便核对。角色语义切换前阻止旧客户端继续授予多 Owner。

## 8. 必须覆盖的验收

- 团队/项目各自唯一负责人；管理员不能操作同级、负责人或自行提权。
- private/team_read/team_write × 内部/外部 × 显式/继承角色组合；显式 Viewer 在 team_write 下仍只读。
- 策略降权预览包含失去写权限人数；继承成员未完成工作时阻止降权，负责人和显式协作授权不受影响。
- 外部用户只访问被授予的项目；团队角色不自动授予项目管理权；撤销显式配置时正确提示恢复的默认权限。
- Viewer 对所有写入口被拒绝，包含原文档作者、旧 CLI、任务提交、上传、评论与 Run。
- 跨项目编码、查询参数、搜索与附件不泄漏无权项目；归档内容只读，所有权治理仍可执行。
- 创建者身份不随转移改变；接收、取消、过期、重复接受与并发转移均正确，只能一次生效。
- 注销覆盖全部所有权与归档项目；预检后的并发授权无法留下孤儿项目；紧急禁用立即成功并可审计恢复。
- 团队移出先处理项目负责人和工作交接；显式外部协作保留必须明确，重入团队不自动恢复旧管理员角色。
- 旧多 Owner、缺创建审计、外部成员与外部 Owner 均有明确迁移结果；历史正文、版本和作者引用不变。

对应回归入口为 `permission-members.test.mjs`、`permissions-policy.test.mjs`、`permissions-ownership.test.mjs`、`permissions-execution.test.mjs` 及 CLI 的 `permissions-cli.test.mjs`。数据库测试共用测试库，按单进程序列运行；不能与其他会清理测试表的测试进程并行。
