# 迁移前的平台 API 退出边界

版本1.0，2026-11-18。需求`XPN8Q792Z2Q8SKA50QZA`，任务`67NGJ43KR8RJP2CQ4FPV`。

平台以`SIGTERM`或`SIGINT`开始退出。Fastify进入closing后拒绝新的HTTP请求；停止监听后客户端也可能收到连接关闭或拒绝连接。Web、CLI、MCP与Hook共用这个入口，不能以只停Web代替停写。

`preClose`先停止资料索引、会话抽取和双引擎投影的新轮询，以及系统Agent/代码分析worker的新claim。各worker的停止请求先发出，不等待前一个worker后才停下一个。`onClose`等待在途HTTP和已开始的后台工作，再关闭平台持有的数据库连接。借用外部数据库的调用者仍负责其连接生命周期。

资料索引即使未启用记忆整理也会运行，因此`TSP_MEMORY_ENABLED=0`不是停写开关。系统Agent/代码分析沿用原有中止和租约约束，不把中止改为成功，不发布晚到结果。会话/投影已持久化的排队与待重试状态保持，不为迁移把它们批量标为完成。

采集模型请求本身允许45秒。信号退出给完整关闭流程75秒，Compose和受控部署脚本给API终止90秒。75秒不是完成保证：在途模型请求、引擎调用、HTTP请求或数据库收尾若超限，进程输出安全原因并以非0退出；关闭失败同样非0。重复信号只触发一次关闭，直到关闭完成前保留信号保护。超时计时器保持引用，避免只有悬挂Promise时错误地自然退出为0。

`docker compose stop`自身成功不表示应用正常退出。部署脚本在停止前记录旧API的容器ID，停止后逐个核验其已退出、非运行、退出码0、没有OOM标记；退出1、SIGKILL137、仍运行或状态读取失败均在备份/迁移前终止。首次部署没有旧API容器时跳过该项。原有应用回退只用于恢复服务，不会在失败后继续备份，也不会自动恢复数据库。

## 如何判定可以备份

该改动只提供平台API这一写入者的退出前置。迁移编排仍须确认API已正常退出、没有同目录其他writer，并单独完成Tencent Wiki/Core、OpenViking内部后台队列和持久存储的退出。只有这些条件都通过，才能在同一静默区间创建PG和完整引擎workspace备份；任何超时、非0退出或未确认writer都不能记为一致性批次成功。

原持久job和lease用于恢复，不能把进程被强制停止说成队列已排空。源与目标不得同时收写。此任务没有迁移业务数据、切换模型或启停当前服务；Linux制品、容量与双引擎drain见后续部署任务。[容器部署与迁移设计](83-server-deployment-and-migration.md)的其他约束仍适用。

## 验证边界

生命周期回归用可控时钟覆盖模型45秒窗口、成功清理和超时非0；真实Fastify HTTP测试覆盖退出时拒绝新写入、已接受请求完成。后台循环测试覆盖单次在途、失败恢复、先停止全部轮询再等待、数据库最后关闭和重复关闭。既有系统Agent/代码分析测试验证中止后不发布晚到结果。数据库测试只能走专用55432测试集群和租约身份守卫，不使用业务库或真实供应商输入。

这些测试不等于已完成服务器全服务容量测试或业务备份恢复演练。部署脚本的应用备份流程也不替代双引擎的一致性迁移窗口。
