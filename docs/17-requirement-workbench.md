# 需求工作台交互设计

- 状态：Adopted（已采纳；进入 docs/07 Spike 1 实现条目）
- 日期：2026-08-13
- 关联：[从需求讨论到开发交付](11-requirement-to-delivery-workflow.md)、[编排工作台交互设计](14-orchestration-workbench.md)、[同步提示与验收/交付视图设计](16-sync-alerts-delivery-views.md)
- 若与架构基线或已接受 ADR 冲突，以基线和 ADR 为准

## 一句话结论

需求工作台是 5 决策点中唯一「讨论与事实并存」的双态界面：讨论过程（对话、草稿、Agent 提取结果）与已确认事实（Requirement Revision）在同一界面共存，但视觉上绝对分界。全平台只有这里允许「非事实」存在，核心交互任务是让「从讨论到确认」的跳变清晰可见——讨论随便聊，只有确认动作产生事实（docs/11 责任边界 1 的界面语言）。

## 1. 界面结构

```text
需求工作台（Feature 级）
┌─────────────────────────────────────────────────────┐
│ Feature 摘要条：目标 / 范围 / 当前需求数 / 待澄清数      │
├────────────────────────┬────────────────────────────┤
│ 对话区（约 45%）         │ 需求表（约 55%）             │
│                        │                            │
│ 人与需求分析 Agent 讨论  │ REQ-0142 邮箱登录  r3 已确认 │
│ （SSE 流式 + Markdown） │ REQ-0147 锁定策略  r1 待澄清 │
│                        │ REQ-0150 重置密码  draft    │
│ ── Agent 提取结果卡 ──   │ （点击行 → 右侧展开 Revision）│
│ ┌────────────────────┐ │                            │
│ │ 候选需求 + 澄清问题 │ │  Revision 历史（不可变）      │
│ │ 冲突提示 + 来源标注 │ │  + diff 视图               │
│ │ [确认] [编辑] [追问]│ │                            │
│ └────────────────────┘ │  状态徽章随流转更新           │
└────────────────────────┴────────────────────────────┘
```

核心区分：**提取结果卡是「卡片」（半成品、可丢弃），需求表是「表」（事实、不可变 Revision）。** 卡片可以随时消失，表只增不改。

## 2. Agent 提取结果卡（从讨论到事实的过渡态）

```text
┌─ 候选需求卡 ──────────────────────────────┐
│ 标题：登录失败统一响应与锁定               │
│ summary：账号不存在与密码错误返回相同响应； │
│          第 5 次失败锁定 10 分钟           │
│ 来源：对话 [第3轮] 「错误提示不能暴露账号状态」│  ← 每个字段可回看来源，防幻觉需求
│                                           │
│ 候选验收标准：                             │
│  AC-1 两种失败返回相同响应 [来自对话]        │
│  AC-2 锁定 10 分钟 [Agent 推断 ⚠]          │  ← inferred 标注
│                                           │
│ 待澄清问题（clarifying）：                 │
│  Q1 锁定计数是否跨设备？（无来源，需确认）   │
│                                           │
│ 冲突检测：与 REQ-0147 范围部分重叠 ⚠       │
│                                           │
│ [确认 → 写入需求表] [编辑后确认] [追问] [忽略]│
└───────────────────────────────────────────┘
```

设计要点：

- **来源标注**是防幻觉的关键：每个字段标注「来自对话哪一轮 / Agent 推断 / 来自某契约」，人一眼分辨哪些是 Agent 编的（inferred）、哪些是本人说过的；
- **待澄清问题独立成区**：未回答前卡片处于 clarifying，不把「未决问题」混进需求正文（衔接 docs/13 的显式未知区原则）；
- **冲突检测**：与已有需求、决策、接口的冲突（docs/11 要求）；MVP 用稳定 ID 引用和术语匹配做确定性检测，不引入 embedding 相似度；
- 「忽略」即丢弃卡片，不进任何事实，讨论记录只留对话区。

## 3. 需求表（持续需求表的界面形态）

```text
┌ 需求表 ─────────────────────────────────────────────┐
│ ID        │ 标题           │ Rev │ 状态      │ 开放问题 │
│ REQ-0142 │ 邮箱登录       │ r3  │ confirmed │ 0       │
│ REQ-0147 │ 失败锁定策略   │ r1  │ clarifying│ 2       │
│ REQ-0150 │ 重置密码       │ --  │ draft     │ 3       │
└─────────────────────────────────────────────────────┘
点击行 → 右侧面板：
  Revision 历史（不可变列表）
    r3 补充锁定策略（当前生效）  ← diff 按钮
    r2 补充统一失败响应
    r1 初始草稿
```

- 状态徽章：`draft / clarifying / confirmed / implementing / delivered / change_proposed / deprecated`（docs/11 状态机）；
- 每一行是「稳定 ID + 当前 Revision」的投影视图——需求表不存储状态，由 Revision 事实派生（架构不变量 8）。

## 4. Revision diff 与变更确认

已确认需求被提议修改时，不是改原文，而是生成新 Revision 提案：

```text
REQ-0142 r3 → r4（提案）
  + 补充：锁定计数在密码重置后清零
  理由：与 REQ-0147 的锁定策略保持一致
  影响：TASK-301、TASK-302 基于 r3 → 确认后标记 stale（联动 docs/16）
[确认 r4] [打回并附原因]
```

- 确认后新 Revision 生效，旧版保留不可变；
- 确认时自动联动 docs/16 的 stale 计算：基于旧 Revision 的任务立即收到「需求基线变更」提示。

## 5. 关键交互流

```text
循环 A（从讨论到确认）：
  人在对话区描述想法
  → Agent 提取候选需求卡（含澄清问题 + 冲突检测 + 来源标注）
  → 人在对话区回答澄清问题 → Agent 更新卡片
  → 人确认 → 需求表新增 Revision（confirmed）

循环 B（变更管理）：
  confirmed 需求需要变更
  → 生成新 Revision 提案 + diff + 影响提示
  → Owner 确认 → 新 Revision 生效 → 基于旧版的任务标记 stale
```

## 6. 与决策点②的衔接

confirmed 需求行尾有「拆分任务」按钮 → 携带该 Revision 跳转编排工作台（docs/14），编排对话条自动带入「基于 REQ-0142 r3 拆分」的上下文。工作台之间的跳转是显式的、带版本的，不靠 Agent 记忆。

## 7. 边界情况

| 边界 | 处理 |
|---|---|
| 多个 Agent/人提取重复需求 | 冲突检测提示范围重叠，人选择合并到已有 REQ 或新建 |
| 确认时发现该需求已有 change_proposed | 确认动作被拦，先裁决变更提案 |
| 讨论记录与事实混淆 | 界面双态分界 + 卡片只可「确认进入表」，不可「拖进表」 |
| 旧 Revision 被新 Revision 取代 | 旧版永久保留，仅当前投影指向新版 |
| 对话区上下文过长 | MVP 只保留最近 N 轮进入 Agent 会话上下文，历史讨论可检索但默认不注入 |

## 8. 技术约束

- 对话区 SSE 流式 + Markdown，与 docs/14 编排对话条同技术形态，不引入 AG-UI；
- 提取结果卡 = PROPOSAL 语义（facts / assumptions / impact，docs/05 已有结构）；
- 确认 = 领域用例「确认 Requirement Revision」，权限 Owner（docs/11）；
- 需求表、状态徽章、待办计数全部事实派生，零新增状态字段。

## 10. 开放问题

1. 「最近 N 轮」的默认值与按 Feature 覆盖策略。
2. 冲突检测的术语匹配规则（同义词、缩写）MVP 做到什么程度。
3. 需求表在 Feature 级与 Project 级（跨 Feature 视图）的关系。
4. 提取卡批量处理（一次对话提取多条需求时）的交互。
