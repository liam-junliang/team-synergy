# 产品定位

## 要解决的问题

当个人或团队同时使用 Codex、Claude Code、OpenCode 等 Agent 工具时，协作容易出现：

- 每个 Agent 对需求、接口和进度的理解不同。
- Agent 的临时文件、未完成代码和正式产物混在一起。
- 多个 Agent 共用目录，导致代码、上下文和权限相互污染。
- 任务完成依赖 Agent 的口头声明，缺少验证证据。
- 不同人的经验值得保留，但其 Agent 难以围绕同一项目事实协作。
- 为解决上述问题直接引入复杂调度、消息和权限系统，早期成本过高。

## 产品定义

本项目是一个轻量的多 Agent 项目协作控制面：

- 管理项目、功能、任务、执行记录和验收状态。
- 为 Agent 生成统一但按角色裁剪的功能上下文。
- 为每次任务执行创建隔离工作区。
- 接收 Agent 提交的正式产物和验证证据。
- 让不同 Agent 工具通过统一 API、CLI 和 MCP 接入，并由本地执行面通过 Agent Client Protocol 或 CLI Adapter 控制会话。

它不是：

- Agent 群聊产品。
- 通用大模型网关。
- 第一阶段就具备完整能力的分布式 Runner 平台。
- 用多个 Agent 取代项目责任人的系统。

## 目标用户

### 第一阶段

- 一个人身兼产品、开发、测试和运维角色。
- 在一台或多台电脑上使用多个 Agent 工具。
- 希望降低上下文重复说明和工作区混乱。

### 后续阶段

- 2～10 人的小型研发团队。
- 每个人保留自己的 Agent、Prompt、模型和个人知识库。
- 团队需要统一项目事实、任务边界、质量证据和决策记录。

## 核心价值

平台不要求所有 Agent 具有相同观点，只要求它们明确区分：

- `FACT`：有来源支持的事实。
- `ASSUMPTION`：尚未确认的假设。
- `PROPOSAL`：等待评审的方案。
- `DECISION`：已经生效的项目决策。
- `ARTIFACT`：任务产生的正式结果。
- `EVIDENCE`：证明结果满足要求的材料。

在团队 Vibe Coding 场景下，核心价值进一步聚焦为两点（详细讨论见 [docs/12](12-team-vibe-coding-context-sync.md)）：

1. **消除上下文衰减（代差）**：多人多职责、多 Agent 环境下，信息在「人 → 文档 → 人 → Agent」的多跳转述中逐层失真；平台通过「确认即事实、事实即上下文」把转述跳数从 N 降到 1。
2. **去黑盒**：通过「快照绑定 + 偏差回流」把 vibe coding 的不可见过程变成可见的版本差异——每个 Run 记录基于哪版事实执行、回流了哪些候选变更。

## 设计原则

1. 项目共同状态是唯一权威协作中心。
2. 工作区属于 Task/Run，不永久属于 Agent。
3. Agent 私有工作过程默认不进入项目共同状态。
4. 项目状态只能通过显式提交和发布更新。
5. 完成状态必须由产物与证据支撑。
6. Agent 权限不能超过所属人的权限。
7. 先以简单闭环解决真实问题，再增加自动化复杂度。

## 产品边界

平台由两个逻辑平面组成：

- **项目控制面**统一任务、决策、产物、证据和审计事实。
- **本地执行面**负责 Agent Session、Git Worktree 和临时文件。

这是职责边界，不代表第一版要部署成分布式系统。单人 MVP 可以把它们安装在同一台电脑上。
