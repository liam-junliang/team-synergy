## 独立语义裁决

先用 `inspect` 生成复核包，再保存逐题 `manual-review.json` 与经校验的 `scorecard.json`。分数只来自最终公开解释/关系，私有事实不能直接加分。源码用来验证，不把“接手者自行打开源码后能回答”算成图已经解释。

| 指标 | 基线 | 新版 | 证据 |
| --- | --- | --- | --- |
| 12 题总分 | 14/36 | 待评 | manual-review / scorecard 与图 SHA |
| 具体规则解释（≥2 分） | 2/12 | 待评 | 正常/拒绝条件与实际定义逐条比对 |
| 接手完整（3 分） | 0/12 | 待评 | 为什么改、下游影响、如何验证及来源 |
| 严重错误断言 | 本组受审题未发现 | 待评 | 无依据因果、身份/权限误读、确认即完成等；缺失与错误分开 |
| 模块职责合理性 | 2/5 | 待评 | 职责重叠、数据所有者、UI/API/usecase/persistence 是否一致 |
| 跨文件/跨批依赖综合 | 1/5 | 待评 | 独立工作流追踪，不只 import 边 |
| 来源可追溯 | 3/5 | 待评 | 来源支持业务断言的精度与充分性 |
| 接手有用性 | 1/5 | 待评 | 空白接手者对 why / downstream / how-to-verify 的回答质量 |

验收门槛保持不变：**至少 27/36、至少 9/12 题达到 2 分、受审关键题零严重错误断言**。结构通过不替代语义门槛；源覆盖不等于正确率。达到这组题门槛也不宣称“理解 95% 项目”或企业级成果保证。

## 新发现与处理

每项分别记录：实际公开断言 → 原始定义/调用关系证据 → 正确解释 → 严重程度 → 用户影响 → 修订后复核。新增样本作为补充发现，不回填或更换冻结题来提高当期分数。
