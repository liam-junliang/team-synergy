## 图谱能给接手者多提供什么

从 22 条有源码依据的规则中提出 17 条关系。原型只展开一跳，记录关系出处和两端资料修订。用当前资料 API 复查权限及版本，用已授权代码运行复查源码快照。异项目、私有端点、撤回端点三个构造用例均被过滤。账号私有业务数据未用于试验。[检索对照](graph-trial.json)

交接漂移、方案采纳和失败测试转缺陷三个场景各有一对独立空白会话。两组均通过本地 Magpie 请求 DeepSeek V4.1 Flash，拿到相同的起始规则和 grep 结果，最多可额外查两次。关系组另外拿到该规则所有相邻提议及对应短说明。独立审阅者在隐藏组别后查阅固定源码。

| 场景 | 常规检索 | 增加一跳关系 |
| --- | --- | --- |
| 交接包已就绪后资料又变了 | 找到漂移阻断及清空回执，遗漏再次 ready | 补出再次 ready，但把两项 ready 阶段的校验写到了 activate |
| 讨论已确认能否证明实现 | 把任务证据误作写验收条件和记忆投影的前提 | 找到任务自测、产物与验证规则，仍夸大了任务证据对投影的影响 |
| 测试失败后如何进入回归 | 找到修复任务门槛，把关联请求幂等误作回归执行可重放 | 区分了关联请求，仍把从测试结果追溯的路径泛化成所有缺陷的前置条件 |

三组常规检索都能直接找到代表性测试位置。一跳展开主要补充跨流程关系，本次累计输入从 5,603 增至 7,051 个模型报告的 prompt token。每组仅运行一次，两组均已给出真实修订，引用正确仍可能伴随业务解释错误。[六份原始回答](answer-comparison.json)

针对方案采纳，又用一份只含类型、方向、规则编号和来源的短关系卡复测。模型主动 grep 第二条规则，分别说明采纳事务和任务状态机的条件，纠正了前置条件误判。此次用了一次额外查询、2,793 个累计输入 token，尚无降低总上下文成本的证据。[短关系卡复测](thin-edge-followup.json)

## 适合先做的产品范围

在 PostgreSQL 中保存有出处的版本关系。先支持“规则依据哪份修订”“哪个测试检查这一条件”“哪一版结论替代了哪一版”。允许明确标记为推断的 `related` 边引导 Agent 读原文。只有能在来源中核验明确门槛时，才记录具有方向的依赖。检索默认沿用现有记忆与资料查询，需要解释下游或验证时，按需展开一跳。

每条边携带两个不可变修订或固定代码锚点、关系类型和方向、证据位置、作用域与状态。读取须校验边和两个端点的可见性；撤回、替代或失去权限时停止展开。项目边和个人边各自遵循现有作用域，私有经验晋升为共识需引用单独创建的共享来源。TencentDB 和 OpenViking 继续提供候选召回。此次已上线的是文档及源码图，语义记忆关系仍处于本地验证阶段。
