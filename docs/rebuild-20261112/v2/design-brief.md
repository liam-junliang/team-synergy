# TeamSynergy 高阶设计背景与模块职责

## 要解决的协作问题

团队希望把一个软件项目从讨论带到可验证的交付。产品负责人要看懂决定的来由，研发成员要知道当前任务使用哪版需求，测试人员要能把失败结果追到修复和回归，接手成员的 Agent 要能按权限找回相关资料。本文把操作者描述的这些目标作为产品意图。下表是为逆向分析制定的职责划分；每项实际支持的行为、例外与空白在对应模块以源码取证。

## 系统架构设计

成员从平台 Web、设备 CLI 或成员自带 Agent 发起操作。项目、成员和任务形成协作范围。业务服务依据身份、项目权限、对象状态和版本写入持久记录。开发执行还涉及本地工作区、设备和 Git，需要远端记录与本地回执互相核对。原件保留在各业务模块；资料索引、代码图和记忆帮助成员按需找到有权读取的证据。部署、权限与治理贯穿整条链路。

| 层次 | 负责的问题 | 应能回答的设计问题 |
| --- | --- | --- |
| 成员入口 | Web 查询与管理，CLI、MCP 和原生宿主接入 | 身份和项目如何绑定？用户看到的动作需要什么授权？ |
| 项目业务 | 规划、需求、设计、任务、交接、验证与缺陷 | 谁持有当前状态？讨论、决策、执行、验收各以什么为凭？ |
| 执行与知识服务 | 成员设备和工作区、后台系统 Agent、代码分析、资料与记忆检索 | 哪些结果异步产生？Agent 如何发现、复查和引用指定版本？ |
| 持久化与治理 | 业务表与修订、操作记录、投影作业、外部语义检索 | 哪个系统能解释事实？怎样发现过期来源、重复请求或权限变化？ |

## 功能模块及预期职责

| 编号 | 模块 | 用户目标与预期功能 |
| --- | --- | --- |
| M01 | 账号、登录与设备身份 | 登录、授权设备、管理身份和会话，判断凭据何时失效 |
| M02 | 团队、项目与所有权 | 建团队和项目、管理成员与继承权限、办理所有权转移 |
| M03 | 项目首页、规划与仓库 | 从背景与指引入手，组织模块、阶段、里程碑和 Feature，定位仓库与工作空间 |
| M04 | 想法、议题与需求基线 | 从讨论到决定、需求与验收条件，评审文档、冻结需求版本 |
| M05 | 原型与架构设计 | 维护设计版本、原型资源和架构图，核对设计依据 |
| M06 | 资料库与文档质量 | 管理目录与修订、跨业务资料检索，查看可引用来源和质量结论 |
| M07 | 任务与执行证据 | 创建与分配任务、领取与执行、提交产物、自测及验收 |
| M08 | 本地运行与成员交接 | 管理设备租约与工作区，将进行中的工作交给另一成员并处理版本漂移 |
| M09 | 测试与缺陷 | 维护用例与资料、记录指定版本的执行，从失败记录走到缺陷修复和回归 |
| M10 | 代码理解与规格接入 | 固定仓库快照、建立代码图、逆推候选规格、评审核对后写回项目 |
| M11 | 系统 Agent 与技能 | 配置系统 Agent 的工作，核对建议及采纳，管理可供任务使用的技能版本 |
| M12 | 管理、审计与系统运维 | 管理平台配置、治理对象、查询操作依据，理解接入和分发条件 |
| M13 | 项目共识与账号记忆 | 从会话提取讨论与经验，控制共享、采纳、撤回与按需检索，区分历史偏好和当前授权 |

## 用什么粒度推导需求

每个模块从用户要完成的操作开始。沿可见入口追到权限判断、持久化和结果，再反向写成能验收的功能要求。以“准备好的交接包遇到资料变动”为例，验收应能指出谁发现漂移、哪个步骤被阻止、谁能处置、接手人何时要重新确认。存在测试定义、代码实现、真实运行和产品意图各有独立依据。无法从代码确认的业务动机、使用频率或线上效果列为待确认。
