# 部署、降级与恢复验收

| 发布或运行情境 | 操作员的检查与可观察结果 | 升级或回退条件 |
| --- | --- | --- |
| 新环境启动 | Compose 先启动带持久卷和健康检查的 PostgreSQL，经单独迁移服务完成后启动 API；前端依赖 API 健康。检查实际容器状态和 API /ready。 | 数据库不可用或迁移未就绪时保持服务未就绪；核对目标库及迁移版本再恢复流量。见 `compose.yaml:3-54`、`apps/core-api/src/server.ts:180-195` |
| 识别后台服务是否运行 | 核对服务是否自建 DB 连接；原生资料索引维护、会话采集和语义投影有独立条件。资料写入成功后检查源修订、任务队列、外部回读。 | 记录哪一步未完成。引擎不可用时按平台可核验来源服务，依据检索头说明降级，不把排队记为已同步。见 `apps/core-api/src/server.ts:204-246`、`apps/core-api/src/routes/memory.ts:38-76` |
| 检查外部读取与隔离 | 从成员身份查资料目录和当前修订，再用独立账号、旧修订或另一项目复查。对私有记忆核对所属账号和适用范围。 | 撤回、越权、旧绑定不得因外部命中而恢复可见性。索引回补后再用同组输入核查。见 `packages/application/src/memory-slice-use-cases.ts:287-311`、`apps/core-api/src/routes/project-materials.ts:11-42` |
| 测试前分配独立资源 | 从仓库运行 `node scripts/run-tests.mjs -- node --test --test-concurrency=1 <测试入口>`。预先检查独立集群与连接身份，记录分配和清理结果。 | 如果上下文身份或目标数据库不匹配，停止测试写入。多个会重置表的测试文件不可并行占用同一测试库。测试结果需写明利用实际服务、替身还是静态解析。见 `scripts/run-tests.mjs:12-32`、`scripts/run-tests.mjs:54-65` |
| 针对破坏性变更做恢复演练 | 先清点业务资料和外部副本；针对本次范围备份；在隔离环境还原，比较业务对象、修订、哈希及非目标数据。再安排停写窗口、复核最终快照，变更后回读业务 API、CLI/MCP 和引擎。 | 本项目早先的文档重建曾在停写前发现队列摘要变化并重做备份。已验证的演练覆盖那次本地库和引擎；上线环境的恢复目标和允许停机时长须单独确认。 |

交付时由发布负责人记录环境、应用与数据库版本、授权范围和停止条件；由业务负责人决定风险接受。当前可核查项包括就绪状态、失败任务、未清理来源数和文档版本一致性。本轮未测出的峰值吞吐、恢复时长、可用率和保留期限，均不能据源码推导成承诺。
