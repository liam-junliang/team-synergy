# 编排工作台交互设计

- 状态：Adopted（已采纳；MVP Web 范围已更新进 docs/00/07）
- 日期：2026-08-13
- 关联：[从需求讨论到开发交付](11-requirement-to-delivery-workflow.md)、[项目上下文图](09-project-context-graph.md)、[团队 Vibe Coding 的上下文同步与 Agent 执行模式](12-team-vibe-coding-context-sync.md)
- 若与[架构基线](00-architecture-baseline.md)或已接受 ADR 冲突，以基线和 ADR 为准

## 一句话结论

编排工作台是「审阅界面」，不是「创建界面」。传统工具（Jira/Linear）为人工录入任务设计，交互重心在高效创建；vibe coding 时代人的角色变成「审阅 Agent 的拆解 → 微调 → 确认」，因此交互重心是**建立信任快**——用最少精力判断「Agent 拆得对不对、哪里要改、确认哪些」。编排对话条与交互依赖图进入 MVP。

## 1. 五条交互原则

| 原则 | 落到界面上 |
|---|---|
| 可追溯 | 每条候选 Task 带来源：基于哪条 Requirement Revision、哪个 Decision、为什么这么拆 |
| 可一步覆盖 | 任何字段内联可改；也可整包打回重拆 |
| 显式确认 | Agent 输出永不自动生效，「确认并分派」是显式动作 |
| 风险前置 | 确认前自动检测：缺验收标准、scope 重叠、循环依赖——拦在确认按钮之前 |
| 最小操作量 | 批量/分组确认 + 内联编辑，目标体验：「5 分钟审完 10 个任务」 |

风险前置直接实现架构不变量「没有验收标准的 Task 不能进入 ready」——不是靠人自觉，而是确认动作本身过不了。

## 2. 界面结构

```text
编排工作台（Feature 级）
┌─────────────────────────────────────────────────────┐
│ Feature 摘要条：目标 / 范围 / 快照版本 / 需求 Revision  │
├───────────────────────────────┬─────────────────────┤
│ 候选任务流（约 55%）            │ 交互依赖图（约 45%）   │
│                               │                     │
│ ┌ 候选卡片 ────────────────┐  │  Cytoscape.js        │
│ │ TITLE scope 验收 负责人  │  │  · 任务节点 + 依赖边  │
│ │ 依赖 置信度/来源标注      │  │  · 拖拽连线          │
│ │ [内联编辑] [拒绝]        │  │  · 循环检测红线      │
│ └──────────────────────────┘  │  · diff 视觉呈现     │
│                               │                     │
│ ┌ 候选卡片（差异高亮）───────┐  │  风险提示列表：       │
│ └──────────────────────────┘  │  ⚠ scope 重叠       │
│                               │  ⛔ 缺验收标准       │
│ [确认选中 N 项] [全选] [打回并附原因] │                │
├───────────────────────────────┴─────────────────────┤
│ 编排对话条：绑定当前 Feature + 方案版本，支持卡片引用   │
└─────────────────────────────────────────────────────┘
```

- **候选卡片**用 docs/11 的 Task 契约字段（title / scope / acceptance / dependencies / profile），每个字段带来源标注：`confirmed`（来自已确认需求/决策）vs `inferred`（Agent 推断）。人优先看 inferred 字段——那是偏差高发区。
- **差异高亮**：Agent 方案与当前任务集的 diff——新增、修改、建议删除分别呈现，人不会漏看「Agent 想改什么」。

## 3. 编排对话条（MVP 范围）

### 3.1 定位

不是通用聊天，而是绑定「当前 Feature + 当前方案版本」的编排对话。用途：对拆解不满时直接对话重拆——「任务 3 和 4 合并」「按接口拆」「给任务 2 补性能验收标准」。

### 3.2 交互要点

1. **卡片引用**：点选候选卡片后可引用进消息（如 `[T3]`），人的表达成本最低；Agent 的回复也能引用卡片并附差异预览。
2. **打回入口合一**：单卡拒绝与整包打回都通过对话条发出，原因自动附带；Agent 重拆产出方案 v2，diff 视图只显示 v1→v2 差异。
3. **候选不直接生效**：对话产出的一切仍是候选（Proposal v2），生效仍须「确认并分派」。
4. **讨论留痕**：对话记录绑定方案版本作为 Discussion 留痕（讨论不是项目事实，但可追溯；打回原因进入下次拆解的上下文，衔接 docs/13 的「已知坑」回流）。

### 3.3 技术形态

MVP 使用 SSE 流式输出 + Markdown 渲染，不引入 AG-UI（[架构基线](00-architecture-baseline.md)将 AG-UI 定为后期统一 Web Agent 流式交互的方案；届时对话条迁移到 AG-UI，交互语义不变）。

## 4. 交互依赖图（MVP 范围）

### 4.1 范围界定

MVP 的交互图仅覆盖**任务依赖图**（候选任务节点 + 依赖边），不是全 Context Graph 的编辑。拖拽连线的操作对象是候选方案——它本来就是未生效的 Proposal，因此不违反 docs/09「权威图只读、编辑行为必须形成结构化 Graph Delta」的原则：拖拽修改的是提案内容，确认后才生效。已确认任务的依赖变更仍需走 Proposal/Decision，与 docs/09 一致。

### 4.2 交互要点

1. **拖拽连线 = 结构化依赖变更**：每次拖拽记录为对方案版本的修改项（谁、哪条边、从什么改成什么），确认时统一生效，不产生「拖一下就直接改库」的隐式写入。
2. **实时循环检测**：拖拽形成循环依赖时立即红线高亮并禁止确认，而不是确认时才报错。
3. **diff 视觉呈现**：新增任务为虚线节点、修改任务高亮、建议删除任务划掉——图上直接看到方案差异。
4. **布局**：dagre 分层布局，适配单 Feature 约 10 个任务的规模。

### 4.3 技术选择

Cytoscape.js（docs/09 已选型）：同时支持图遍历、集合过滤与多种布局。MVP 只用于任务依赖图；P1 扩展只读 Context Graph 视图时复用同一组件。

## 5. 关键机制

1. **方案版本化**：一次拆解 = 一条 Proposal，可多次重拆；确认绑定具体版本；打回原因进入下次拆解上下文。
2. **部分确认 + 批量操作**：允许只确认一部分，其余留在候选区；确认是原子事务（批量创建 Task + Assignment，见 docs/11），不存在「一半成功」。
3. **打回两种粒度**：单卡拒绝（附原因）→ 只重拆该卡；整包打回（附原因）→ 重新拆整个 Feature。
4. **与决策点③合流**：确认分派时顺带设置授权模式。MVP 只有「单次 Claim」；P2 引入 Claim Policy 后，授权选项（单次 / 带预算委托）出现在同一确认动作里，人不必去另一个页面。

## 6. MVP 范围界定

编排对话条与交互依赖图进入 MVP，意味着 MVP Web 不再是「最薄的状态界面」，因此明确边界：

- **MVP Web 聚焦编排工作台单页**（含确认分派与授权入口）；
- 完整 Web Console（Feature、Task、Run、Artifact、Evidence、Decision 全视图）仍在 P1；
- AG-UI、Cytoscape.js 全 Context Graph 编辑不进入 MVP；
- 依赖：此界面依赖 Spike 1 任务闭环先跑通（Core API + Task/Proposal 领域 + SSE 流式通道）。

## 8. 开放问题

1. 对话条中 Agent 重拆的触发边界：多大范围的修改值得重拆 v2，多小的修改应该直接内联改卡片。
2. 方案版本与 Context Graph Snapshot 的绑定关系：重拆时快照是否随之刷新。
3. 循环检测的性能与提示细节（大依赖图下的实时性）。
4. 确认分派后的回滚：误确认的批量任务如何整体撤销。
