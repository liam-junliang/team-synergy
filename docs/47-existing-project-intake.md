# 从代码梳理现状规格与存量项目接入

日期：2026-10-18。状态：**第一版已实现代码规格候选、审阅冻结、新增/关联发布和 tsp 接入。存量项目资料未清理；自动更新已有正文与三方合并仍属于后续阶段。** 操作步骤见 [代码规格接入操作指南](48-code-spec-intake-guide.md)。

## 1. 决策与目标

建设「代码规格」能力：成员使用已授权的本机 Agent 阅读项目代码，通过 `tsp` 提交有证据的候选规格，在项目内审阅后发布到已有模块、需求和文档体系。先得到可信的现状描述，再整理存量资料。

核心路径：**绑定仓库 → 固定代码范围 → 生成候选 → 对照已有资料 → 审阅选择 → 发布并留下映射 → 后续比较变更**。

第一版沿用本地执行、平台保存协作事实的边界。平台不增加通用 Agent 调度器，不要求部署一个 Wiki/RAG 服务，也不新增扫描依赖。`tsp intake prepare` 随 CLI 输出版本固定的 `existing-project-intake` 技能；Codex 等本机 Agent 按技能阅读代码并提交结构化结果。已有技能库可以补充经过审核的分析规范，第一版不自动向技能库写入资料。语言支持首先验证当前 TypeScript/React/Fastify/Drizzle 项目，其他语言必须报告识别能力和未分析范围。

## 2. 从当前项目得到的约束

| 已有能力 | 可复用部分 | 必须补齐的边界 |
| --- | --- | --- |
| `apps/cli/src/project-workspace.ts` | 工作空间、仓库绑定、Git 状态 | 分析范围、文件指纹和一次扫描的完整性记录 |
| `apps/cli/src/pack.ts` | 平台上下文下载到本地 | 接入方向相反，需要候选提交协议 |
| `packages/application/src/project-structure-use-cases.ts` | 模块、Feature 与权限规则 | 目前部分写入和审计分开提交；不能靠循环 HTTP 请求提供可靠导入 |
| `packages/application/src/requirement-use-cases.ts` | 需求正文、关联和修订 | 现有更新不完整支持调用者预期版本检查，不能安全自动覆盖 |
| `packages/application/src/requirement-document-use-cases.ts` | 需求文档与版本 | 继续使用需求文档实体与系统目录，不另建重复正文 |
| `packages/application/src/architecture-document-use-cases.ts` | 图源、说明、版本；修订已有行锁和 `baseRevision` | 接入项与实际文档之间需要稳定映射 |
| `packages/application/src/project-access.ts` | 当前有效角色与项目归档判断 | 批次、候选、发布和重试都须重新检查权限 |
| `docs/44-agent-workspace-skills-proposal.md` | 技能版本、项目采用及本机同步 | 接入批次记录实际使用的技能版本，不能随最新版改变解释 |

本次试点基于有未提交改动的工作区。只记录 Git commit 会遗漏大量现状，因此必须同时保存相对文件路径、内容 SHA-256、工作区是否有改动、扫描范围和清单摘要。它是“本次工作区的代码规格”，不能自动代表已部署版本。

## 3. 第一版范围

### 纳入

1. 单个项目、单个已绑定仓库、显式选定目录的一次接入。多仓库先分别建批次。
2. 自动提取业务能力候选、模块/Feature 建议、行为规则、权限边界、接口及数据对象说明、Mermaid 架构候选和测试映射。
3. 代码证据定位、分析盲区、现状与目标的区分，以及重复项和冲突预览。
4. 发布动作仅支持：**创建模块、Feature、需求、需求文档、架构文档，以及显式关联已有同项目实体**。关联已有实体不改其业务字段。
5. 新需求保留现有草稿生命周期；现状标签是独立证据属性，不能借此标记“已验收”。代码反映的业务规则也不自动成为团队编码规范。
6. 逐项发布结果、幂等重试、失败续传、审计与来源映射。

### 第一版不执行

- 不直接更新或删除已有业务正文，不自动合并同名模块，不清空旧资料。
- 不自动创建或关闭执行任务，不伪造历史想法、讨论、验收、Run、租约或交接。差距可以形成任务建议，之后由正常任务流程创建。
- 不把代码目录等同于产品模块；路由、服务、数据库和测试应共同支持业务划分。
- 不自动把任意网页、代码注释或仓库内指令当作 Agent 的执行指令，不运行仓库脚本来“证明”所有内容正确。测试执行须使用明确范围和隔离环境。
- 不上传整份源码、`.env`、私钥、依赖目录或含凭据的 Git URL。平台保存最少的定位、摘要和经检查的短证据；本机 Agent 使用何种模型服务由用户环境决定，不能承诺所有分析都离线。

已有内容更新在第二阶段引入：先为相关普通编辑路径补齐统一并发检查，再上线三方差异合并。第一版可以展示“建议更新”，发布入口必须禁用该动作，不能退化成覆盖写入。

## 4. 页面与使用流程

入口放在「项目」二级菜单中的「代码规格」。首次使用提示「接入已有代码」，后续显示分析批次、范围、来源版本、候选数量和已发布数量。它服务于所有成员协作，不属于系统管理台。

页面遵循 Web UI 规范的标准阅读结构：左侧批次/候选列表独立滚动；右侧固定操作栏，内容在自己的滚动区域中阅读，正文不得从固定标题上方露出。

一次接入包含五步：

1. **准备**：选择已绑定仓库、目录和分析目标；下载当前可见的模块/需求/文档索引；明确本次不覆盖的目录。展示本机命令和应使用的技能版本。
2. **本机分析**：先盘点入口、业务层、持久层和测试，再分业务提取现状。记录分析失败、未读文件及原因；没有分析到的能力不能被判定为不存在。
3. **上传候选**：校验协议、引用关系、大小、路径和敏感内容；仅进入批次区，不改变项目业务资料。
4. **审阅**：按类型、处理状态与关键词筛选；对照候选与已有正文，查看代码依据和测试证据，明确选择新增、关联或跳过。相似标题只供人工选择，不作为身份依据；第一版不提供自动正文差异合并。
5. **发布**：Owner/Admin 选择批准项，看到冻结的发布计划与依赖关系后执行。每项显示真实业务编码；失败保留已完成结果，可修正未完成项并重新审阅续传。

已实现的命令（提交与发布必须带可重放的请求标识）：

```text
tsp intake prepare --repository <code> --scope <relative-path> --out <directory>
tsp intake validate <directory>/intake.json
tsp intake submit <directory>/intake.json --idempotency-key intake-submit-001
tsp intake preview <batch-code>
tsp intake apply <batch-code> --plan <plan-hash> --idempotency-key intake-apply-001
tsp intake status <batch-code>
```

`prepare` 负责本地清单与平台索引，不偷偷启动未知模型；Agent 负责阅读和产生候选。`apply` 默认不隐式批准候选，要求 Web 已完成审阅并冻结发布计划；CLI 与 Web 使用同一权限及审计链路。可先交付 Web 审阅批准，之后再补 CLI 审阅操作。

## 5. 证据与现状规格

每条候选包含：稳定本地键、业务标题、行为和例外、验收场景、依赖/关联、来源路径与符号、文件指纹、测试引用、未验证事项、目标平台类型。

不要用一个“置信度 95%”替代依据。证据分开记录：

| 维度 | 示例状态 | 含义 |
| --- | --- | --- |
| 实现观察 | `observed_in_code` / `inferred` / `unknown` | 有源码依据 / 推断 / 无法判断 |
| 测试 | `defined` / `passed` / `failed` / `skipped` / `not_run` | 测试定义和本次实际结果分开；绑定命令、时间与代码指纹 |
| 运行环境 | `not_verified` / `verified` | 测试环境或浏览器实际观察，明确环境和范围 |
| 业务审阅 | `pending` / `accepted` / `rejected` | 人员对规格准确性的判断 |

本机上传的测试结果标记为 `client_reported`，平台校验结构和关联，不冒充服务端独立验证。通过测试不能证明没有遗漏，也不能直接认定产品满足生产规格。

来源快照包含 `repository_code`、可用时的 commit、dirty 状态、选定路径、忽略规则、扫描完成度、文件指纹、清单摘要和技能版本。文件行号只是展示锚点；CLI 在校验、提交或替换前重新采集，文件变化即拒绝使用旧快照。首次 `prepare` 分配并持久化仓库 `namespace`；Agent 为候选分配稳定 `key`，重命名标题不改变它，后续通过下载的已有映射复用，不能用标题或绝对路径生成身份。

目录存在但读取失败、扫描中代码变化、未跟踪文件未获选中，都必须明确记录。生成结束时重新校验选定文件清单；输入改变则不能声明是一个一致快照。平台只保存收到的快照事实，无法替用户证明上传后本机没有继续改代码。

## 6. 批次、发布与重试

新增四类持久记录（迁移 `0039_project_intake.sql`，仅增加接入表和索引）：

| 记录 | 核心字段 |
| --- | --- |
| `intake_batches` | 项目/仓库、创建者、来源摘要、技能版本、payload 摘要、状态、批次版本、冻结计划摘要、持久化 `stop_requested` |
| `intake_items` | 批次、本地键、实体类型、候选正文、依赖键、证据、审阅状态、动作、目标编码、当前执行结果 |
| `intake_bindings` | 项目/仓库/namespace/kind/source_key → 业务类型与编码、上次发布指纹、导入来源；组合键唯一，不跨项目复用 |
| `intake_attempts` | 幂等键、计划摘要、逐项结果、失败原因、操作者、执行时间；不记录凭据或本机绝对路径 |

批次状态：`draft → ready → applying → applied / partial`。未执行时取消进入 `cancelled`；执行时停止先持久化 `stop_requested`，当前项结束后根据结果进入 `stopped`（零成功）、`partial`（部分成功）或 `applied`（全部完成）。`partial` 另记失败或主动停止原因，表示已经有真实写入，不能显示为“已撤销”。候选修改、批准变化、目标关联变化均提升批次版本并使旧计划失效；已经成功的条目及映射不可编辑，只能调整未提交项并重新审阅。

### 发布顺序与原子边界

- 预检整批：类型白名单、引用同项目、依赖无环、来源/候选摘要、当前权限、目标存在、计划版本一致；第一版限制 500 项、JSON 10 MiB，证据正文逐项限制。更大范围拆批。
- 排序：模块 → Feature → 文档/架构 → 需求与其链接；依赖失败则后续项标为 blocked，不创建悬空引用。
- 从现有应用用例抽取少量可在指定事务内运行的写入函数，共享业务校验。每项的**业务实体、首版本、审计、来源映射和成功收据**必须同一事务提交。禁止在 CLI 直接写数据库，也不复制一套旁路业务规则。
- 需求文档导入只接收已解析的同项目模块编码/ID，不调用现有 `resolveCompatModule` 的按名称兼容及隐式创建分支。模块只能来自已批准依赖或显式绑定；缺少映射就阻塞，不在文档事务外偷偷创建模块。
- 批次不是长事务。每项执行前重新检查操作者、项目状态、计划和依赖；沿用成员治理的用户 → 团队 → 项目锁序，再锁批次、条目和映射。项目锁仅维持单条提交，不能跨分析或整批。并发发布返回进行中状态或幂等结果，不同时消费同一条目；它不能代替普通业务页面的实体并发检查。
- 系统目录在独立短事务中预建，单条写入器不重复初始化。目录锁与 `0025_context_material_fence` 的业务写入触发器使用同一全局材料锁，不能把它当作只在目录初始化时出现的锁。接入准备和单条发布在取得治理行锁后仅尝试获取材料锁；有竞争时回滚短事务、释放行锁，在事务外有界重试。这样可兼容已有先材料锁的读取/首页路径和先治理行锁的管理路径，避免等待环；数据库死锁或序列化冲突也必须整条事务重试，不能在 savepoint 中误记为业务失败。
- 请求幂等键与 payload/计划摘要绑定：相同请求重放返回已持久化结果，键相同但内容不同返回冲突。来源映射组合唯一约束同时阻止跨用户、跨批次重复创建；遇到已有映射返回绑定/冲突建议，不能创建第二份。断线后读取收据决定是否续传，不能仅靠客户端“上次失败”判断重建。
- 服务重启不依赖进程内锁。`applying` 的恢复先检查持久记录，每次在事务锁下领取下一项前检查 `stop_requested`；已经成功的项不重跑。权限撤销或项目归档后停止继续写，保留先前事实。
- 取消/停止只阻止后续项，正在提交的一项允许完成并回报；确认停止后重启不得启动新项。主动续传须当前 Owner/Admin 发起新 attempt、再次确认权限和计划，然后清除停止标记。已停止或结束的原幂等键不会触发续传；新 attempt 使用新的幂等键，条目收据与来源映射继续复用。第一版 API 统一返回批次当前状态与逐项结果，内部保留各 attempt 收据，但尚无按 attempt 单独查询历史的接口；不能把当前批次聚合结果当作原 attempt 的历史快照。

首版不提供“一键回滚全部”。新增内容若需要撤销，走已有的归档/正常生命周期并保留历史；有后续引用或修改时先展示影响。没有归档能力的实体不能伪称可回滚。第二阶段再做受版本和依赖保护的补偿操作。

### 对已有资料的处理

首次导入允许手动绑定已有实体，需校验类型、项目、有效状态和审阅时指纹，绑定时不改正文。绑定结果必须区分“仅关联”与“已由本批次写入”，不能把现有正文误记为 Agent 产物。

后续阶段计划采用三方比较：上次接受的内容、当前平台内容、新的代码候选。仅新候选变化可建议更新；平台也变化则提示冲突。标题、摘要、模块/Feature 归属等未必推动现有正文 revision，故不能只检查 revision，需覆盖所有受管字段或统一实体版本。源代码删除只产生“疑似过时”提示，不执行删除。第一版仅对照候选与当前资料并保护目标指纹，不实现三方更新。

## 7. 权限

| 操作 | Viewer | Member（含显式外部成员） | Project Owner/Admin |
| --- | --- | --- | --- |
| 阅读已发布业务资料 | 按现有权限 | 按现有权限 | 按现有权限 |
| 查看接入候选及源码定位 | 不开放候选区 | 当前项目可见批次 | 当前项目可见批次 |
| 准备和提交候选 | 否 | 可以 | 可以 |
| 修改未冻结候选 | 否 | 本人批次 | 项目内批次 |
| 批准、关联已有实体、发布/续传 | 否 | 否 | 可以 |

服务端逐次按 `resolveProjectAccess`/`assertProjectAccess` 判定；系统管理员身份本身不提供项目接入权限。创建者不享有永久权限，离开项目后不可查看旧候选或续传。归档项目只允许相应角色读取历史，不再提交、审阅或发布。

“有平台项目权限”不代表“有 Git 仓库访问权限”，本地 Git 凭据由成员自行管理。证据不得夹带跨项目文档、其他仓库源码或凭据。跨团队技能共享不等于跨团队代码/规格共享。

## 8. 落地顺序与验收

### A. 当前评估交付

完成代码边界核对和账号权限/系统管理试点，产出可追溯 JSON 与阅读报告。全部为本地候选，不写线上项目，不完成任何历史任务。

### B. 候选闭环（已实现）

新增协议校验、`prepare/validate/submit/status`、批次存储、固定版本技能和项目内预览。涉及 `packages/contracts`、`packages/persistence`、`packages/application`、`apps/core-api`、`apps/cli` 与 `apps/web` 的各自接入模块；不把分析逻辑塞进现有业务页面。

验收：路径穿越、绝对路径、逃逸符号链接、重复键、跨项目引用、未知 schema、依赖环、敏感字段、超限 JSON 被拒绝；部分扫描和代码漂移可见；中英文及窄屏可读；任何提交均不产生业务实体。

### C. 新增与关联发布（已实现）

抽取事务写入器、实现计划冻结、审阅、逐项收据和依赖提交，再开放 `apply`。先锁定相关已有业务用例的回归测试，不新增框架或替换全项目数据层。

验收：相同幂等键重放不重复写；不同内容重用键被拒；在提交前/提交后断线恢复、服务重启、同时 apply、依赖失败、批准后修改、角色撤销、项目归档都不会产生越权写或孤立映射；取消不隐藏已经成功的条目，取消后重启不继续提交；缺少模块映射时无隐式业务写入；绑定已有实体不会新增正文版本。

### D. 再整理 TS Platform 存量数据（本次未执行）

扩大分析到文档、计划、需求、设计、任务、测试、缺陷、交接、技能与接入等实际业务域；导出当前项目资料及关联，生成“保留 / 关联 / 修订 / 待归档”的预览，保留还原材料。先同步新增事实，旧测试数据清理由单独可审阅的清单执行。历史任务的完成状态必须有独立依据，不能由代码存在反推。

### E. 增量更新（后续阶段）

补齐实体及普通编辑路径的并发版本保护后，加入差异更新、版本回溯和受保护的补偿。Git 变更只决定重点复查范围；权限函数、共享类型或数据模型变化时扩展受影响范围，不能只分析 diff 行。

## 9. 开源借鉴与取舍

| 参考 | 借鉴 | 不直接照搬的部分 |
