# 项目功能模块与里程碑管理

## 背景

当前需求工作台把需求文档的 `module_key` 当作文档分组，同时 Feature 只能由 Agent 或 CLI 直接创建，项目阶段和里程碑没有正式实体与管理入口。这导致需求分析、功能归类和交付计划混在自由文本中，用户无法校正 Agent 的拆解结果。

## 目标

平台需要同时提供两个互相关联的项目视角：

- 需求视角：需求文档 → 需求点 → 功能模块 → Feature。
- 交付视角：项目阶段 → 里程碑 → Feature → 任务。

Agent 可以提出模块、Feature、阶段和里程碑候选项，但正式项目结构必须能够由项目 Owner 在 Web、API 和 CLI 中查阅、创建、编辑、调整和归档。

## 需求工作台

### 文档库与文档目录

- 页面最左侧一列是项目“文档库”，用于搜索、筛选和选择多份需求文档。
- 选择文档后，右侧阅读区的左栏是“文档目录”，根据当前 Markdown 标题自动生成。
- 文档目录只描述当前文档内部结构，不承担多文档导航职责。

### 需求点

- 需求点可以先从文档中提炼，再归类到功能模块和 Feature。
- 新建需求点时不应强制预先存在 Feature。
- 未归类需求点必须能够被筛选并批量归类。
- 需求点保留来源文档和来源修订，确保 Agent 能追溯上下文。

## 功能模块

### 功能模块

- 功能模块是从项目需求中归纳出的稳定功能域，不是文档标签。
- 功能模块属于项目，包含名称、说明、排序和状态。
- 项目 Owner 可以新增、改名、调整说明、排序和归档模块。
- Web 展示模块名称；API 与 CLI 使用平台生成的公开编码。

### Feature

- Feature 是模块下可以独立交付和验收的产品能力。
- Feature 必须能够在页面中新增、编辑、移动到其他模块和归档。
- Agent 可以根据需求点提出候选 Feature；用户可以确认、改名、合并或拒绝。
- 需求点与 Feature 的关联应允许在需求分析后建立，而不是在需求点创建前强制建立。
- Feature 可以设置独立的开始和结束日期；日期不是从里程碑复制出来的展示值。
- Feature 排期必须完整地落在目标里程碑的开始日期和目标日期之间。移动 Feature、调整 Feature 日期或收缩里程碑窗口时，后端都必须重新校验该约束。

## 项目计划

### 项目阶段

- 项目阶段表示较大的交付周期，与任务状态严格区分。
- 阶段属于项目，包含名称、目标、排序、起止时间和状态。
- 阶段可以包含多个里程碑。

### 里程碑

- 里程碑是阶段内明确的结果节点，包含名称、目标、开始日期、目标日期、负责人和状态。
- 一个里程碑可以计划交付多个模块下的 Feature。
- 一个 Feature 只有一个当前目标里程碑；调整计划时可以移动到其他里程碑。
- 如果 Feature 必须跨多个里程碑交付，应先拆分为更小的 Feature。
- 里程碑完成需要关联 Feature 完成验收、没有阻塞性缺陷，并由负责人确认。

### 计划页与甘特图

- 顶部入口使用“计划”，页面默认先回答排期和交付节奏，不再把阶段/里程碑配置卡片作为主体。
- 主视图采用 MIT 许可证的 `@svar-ui/react-gantt` 开源组件，在同一棵树中展示“阶段 → 里程碑 → Feature”。
- 时间轴支持日、周、月尺度；阶段使用起止日期，里程碑使用开始日期和目标日期。
- Feature 使用自己的开始和结束日期绘制甘特条，并且只能安排在所属里程碑窗口内；未填写完整日期的历史 Feature 明确显示为“待安排”，不伪造甘特条。
- 甘特图保持只读；双击行后通过受控弹窗编辑阶段、里程碑或 Feature 的里程碑归属与独立排期，避免拖拽产生未持久化或绕过权限的状态。
- 搜索、阶段筛选、时间尺度和待规划入口统一位于甘特工具栏。待规划 Feature 使用右侧抽屉，不再常驻占用页面面积。

## 需求文档与交接文档

- “需求”中的文档库回答为什么做、做什么，并为需求点提炼提供来源。
- 原“项目文档”入口改名为“交接”，回答如何对接、部署、运行和交付。
- 交接文档主要承载接口/API、部署环境、联调协议、交付清单、运维和验收交接，不替代需求文档。

## Agent 与 CLI

- Agent 查阅和修改实体时统一使用公开编码，不使用数据库数字 ID。
- CLI 必须提供模块、Feature、阶段、里程碑的 list/show/create/update/archive 能力。
- CLI 的 `feature create/update` 使用 `--start-date/--end-date` 写入排期，`feature update` 使用 `--clear-start-date/--clear-end-date` 清空排期；所有实体参数仍只接受公开 code。
- Agent 生成候选结构时不得直接写入自由文本字段冒充正式实体。
- 领取任务生成的上下文包应包含所属模块、Feature、目标阶段和里程碑，以及关联需求文档和需求点。

## 首个交付切片

1. 建立模块、阶段和里程碑正式实体，并将 Feature 关联到模块和目标里程碑。
2. 允许需求点在没有 Feature 的情况下创建，后续再归类。
3. 需求页修正文档库和文档目录层级，增加功能模块管理入口。
4. 新增项目计划页面，支持阶段和里程碑管理及 Feature 分配。
5. 补齐 API、CLI、测试和迁移，并使用本项目自身完成一次端到端任务拆解与交付验证。

## 验收原则

- 页面需要优先展示名称，公开编码只作为次要信息或复制/悬浮内容。
- 用户可以完成“上传文档 → 提炼需求点 → 归纳模块 → 创建 Feature → 安排阶段和里程碑 → 拆分任务”的完整操作。
- Agent 可以通过 CLI 完成相同流程，并能快速查阅所有上游上下文。
- 模块、Feature、阶段和里程碑不再依赖不可管理的自由文本输入。

## 本次狗粮验证发现

本轮改造使用平台自身建立了 Feature、需求文档、需求点和规划/实施任务，并完成了一条规划任务的 Claim、Submit、Verify、Close。验证过程中确认以下产品缺口：

1. 初始实现要求需求创建时先选择 Feature，与“先提炼需求点、再归纳模块和 Feature”的目标流程相反；本轮已改为允许先建需求点，后续再绑定模块和 Feature。
2. 原生子 Agent 与平台任务/Run 没有启动和身份绑定入口，任务编码只能由编排者手工转交。
3. `task claim` 创建 Run 后再次执行 `task run` 会尝试重复 Claim，返回 `claim_run_conflict`；CLI 缺少在已有 Run 中执行或恢复命令的语义。
4. Worktree 以已提交 Git HEAD 为基线，主工作区未提交改动不会进入执行环境；在连续开发且工作树较脏时，Agent 会看到陈旧代码。
5. 新 Worktree 没有依赖和构建产物，必须先安装依赖并按 workspace 拓扑完整构建，单独构建 CLI 包 `@team-synergy/cli` 会因内部包尚无 `dist` 失败。
6. Planner/Builder Run 提交后，需要再次以 `verifier` Profile Claim 同一任务，创建独立验证 Run 后才能 Verify；当前帮助和页面没有清楚表达这一过程。
7. CLI 顶层帮助的命令摘要落后于实际子命令，容易让 Agent 误判 `project bind/current`、`task run/verify/close/history` 等能力不存在。
8. 原生子 Agent 已经启动时，需要一个不创建 Worktree 的 `task attach`，把现有进程、共享工作目录和平台 Run 绑定；本轮已补齐该能力，并要求由领取任务的 Agent 本人 Submit，不由编排者代交。
9. 只有标题、编码和验收条目的任务卡不足以替代子 Agent 的完整提示词。本轮已为任务增加可编辑执行简报、范围和验证接缝，并把需求正文、项目文档、依赖与 Submit 协议组装进 Context Pack。
10. 并行 verifier 同时使用唯一的 `acp_test` 会造成迁移互撞和假失败。“共享资源与互斥约束”应进入任务执行简报或调度器资源锁；同时 verifier 应能记录 `fail` / `inconclusive` 结果，而不是只允许成功 Verify。
11. 初始 Context Pack 只有 Feature、模块、里程碑和阶段编码，没有业务名称，Agent 仍需反查。本轮已在公开 Task DTO 中补齐名称，并保持 HTTP/CLI 边界不暴露数字 ID。
12. `task attach` 的共享工作区 Context Pack 曾错误提示 Agent 进入 Run `repo/`；本轮已按执行模式区分完成定义，共享模式明确使用当前目录，Worktree 模式才使用 Run `repo/`。
13. 执行简报能表达目标与范围，但没有自动注入精确的 API 响应字段层级；两个独立 Agent 都需要再阅读后端实现确认 DTO。后续应把机器可读接口契约或相关 schema 摘要纳入 Context Pack，而不是依赖 Agent 自行检索。
14. 原任务被补救任务替代时，状态机缺少 `rework` / `superseded` 语义。当前可以关闭通过验证的补救任务，但不能准确表达原交付“部分完成、已由后续任务接替”。
15. 任务看板的卡片不应承载完整执行简报。本轮已改为标题加清洗后的两行纯文本摘要，完整 Markdown、验收、范围、需求、Run、证据和产物只在任务详情展示。
16. 项目计划首版同时保留阶段卡片、统计卡片、自绘时间轴和待规划大区，虽然功能完整，但信息层级凌乱且时间轴质感不足。本轮已改为单一开源树形甘特工作区，配置动作收敛到工具栏、弹窗和抽屉。
17. 两个后端子 Agent 在收到完整任务编码与 CLI 领取指令后，仍被继承的上层产品讨论覆盖，只返回方案建议且没有执行 `task attach`；同轮 Web Agent 能正常 Attach、Submit。这说明编排器不能只依赖提示词约定，后续应增加“派发后必须在时限内产生 Run”的握手检查，并在未 Attach 时自动中止或重新派发。
18. 本轮计划页重设计由主 Agent 亲自执行，并通过平台创建任务 `S14ETF6FN0FE9WRQFXD2`、分派、Attach 到 Run `GDEZSEHPY6JAZCBZMHG6`，验证了不依赖子 Agent 也能保留完整任务/Run/证据链。
19. Feature 直接复用里程碑日期会让甘特图看起来有排期、实际上没有执行窗口。本轮新增 Feature 独立起止日期和双向边界校验：Feature 越界会被拒绝，里程碑收缩压到已排期 Feature 也会被拒绝；旧数据保持“待安排”。

下一步优化方向：为任务调度增加共享资源锁、`fail` / `inconclusive` 验证结果、`rework` / `superseded` 状态和派发后 Attach 握手；自动注入机器可读接口契约；提供 `task run --run <run_code>` 或自动恢复活动 Run；对脏工作树提供显式快照策略，并在时间线中更清楚地表达执行 Run、补救任务与验证 Run 的关系。
