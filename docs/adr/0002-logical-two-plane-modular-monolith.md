# ADR-0002：逻辑双平面，MVP 采用模块化单体

- 状态：Accepted
- superseded_by: null
- 日期：2026-08-12

## 背景

项目最终需要同时支持云端共享状态和开发者本地 Agent/文件操作。如果从第一版就拆成云端调度器、常驻 Bridge、消息总线和多个服务，平台复杂度会超过待解决的问题；如果完全不划分边界，后续共享部署又会迫使领域逻辑重写。

## 决策

逻辑上分为：

- Project Core 控制面：项目事实、状态机、审计和共享 API。
- Local Execution 执行面：Agent Session、Workspace、Git 和本地日志。

MVP 物理上采用 TypeScript 模块化单体和本地 SQLite。`agentd` 由 CLI 按 Run 启动，不要求常驻。小团队阶段只把 Core API 和数据库迁到共享服务，并将 Persistence Adapter 切换为 PostgreSQL。

控制面与执行面通过版本化 API/Contract 交互，客户端不得直接访问数据库。

## 结果

正面影响：

- 单人安装和调试成本低。
- 领域边界可测试，未来可以独立部署。
- 不需要消息总线、服务发现和分布式事务。

代价：

- 必须保持模块边界，不能因同进程而跨模块直接修改表。
- SQLite/PostgreSQL Adapter 需要契约测试。
- 常驻后台执行和远程唤醒要等后续阶段实现。

## 被否决的方案

### 第一版即微服务化

引入部署、追踪、重试和数据一致性成本，但尚无规模或故障隔离证据。

### 完全本地脚本且没有 Core API

短期更快，但无法稳定支持不同入口和后续多人共享，会制造多个事实源。
