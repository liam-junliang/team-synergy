# ADR-0009：协作需求文档、需求表与 Agent 拆任务

- 状态：Accepted
- superseded_by: null
- 日期：2026-08-17

## 背景

项目需要同时容纳可连续阅读的完整需求语境和可追踪、可拆任务的需求点。单篇长文难以按模块查阅，只有原子 Requirement 又会丢失背景、范围和跨条目规则。此前把草稿、评审、生效和变更状态放到需求文档上，增加了使用成本，也偏离“协作上传和共享阅读”的定位。

## 决策

采用三段式协作链路：

1. `Requirement Document` 是完整协作文档。一个项目可按模块维护多份 Markdown/TXT，使用稳定 `document_code`、摘要、关键词和 Revision；保存后项目成员立即可读，可通过稳定链接分享。
2. `Requirement` 是需求表中的稳定需求点。外部通过 `document_code` 链回来源文档，服务端保存数字 `document_id` 关系，并记录 Feature、正文、验收标准、待澄清问题和关联任务数。
3. Agent 读取一个 Requirement 后，将其拆为一个或多个 Task。API/CLI 形成 `document_code → requirement_code → task_code` 追溯链，数据库内部保存对应数字关联。

需求文档不承载提交评审、批准生效等流程。作者或项目 Owner 可以编辑，保存时生成新的 Revision 并记录修改说明。需求点和任务保留各自面向交付的状态，不反向污染文档阅读流程。

Agent 采用渐进式加载：先读取轻量 `requirements/index.md`，再读取任务关联的完整来源文档；无明确关联时使用 `requirement-doc search/show`。拆任务使用 `requirement show` 获取结构化需求，再调用 `task create --requirement`。

Web 需求页包含“文档库”和“需求表”两个并列视图。所有上传、新建、编辑、提炼需求点和拆任务操作都在弹窗中完成，页面主体优先用于阅读和列表浏览。

## 结果

- 文档上传、分享和阅读不再受评审状态阻塞。
- 需求点从文档底部的附属信息提升为独立表格，可直接观察验收、待澄清项和任务覆盖。
- 人和 Agent 使用同一条追溯链，CLI 执行任务时仍能定位来源全文。
- Revision 保留协作修改历史，但不强迫团队执行审批流程。

## 被否决方案

- 单一项目需求长文：模块无法独立查阅，Agent 上下文噪声随项目增长。
- 只有结构化 Requirement：缺少完整叙事、范围和跨条目业务规则。
- 在需求文档中内置审批流：与协作型文档定位冲突，并显著增加上传和共享成本。
