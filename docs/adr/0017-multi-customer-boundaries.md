# ADR-0017：共库多客户、显式交付与受控支持访问

- 状态：Accepted
- 日期：2026-10-23
- superseded_by: null
- 依据：用户明确要求多个客户共用数据库，并选择 [RLS 评估](../57-multi-tenant-rls-assessment.md) 中全部三项推荐。
- 范围：固定产品与数据边界，约束后续实现；**不表示 RLS、tenant schema 或租户事务已上线**。
- 兼容：在 ADR-0007 的团队/项目/工作空间层级外增加客户边界，不把 team 等同客户；不取代 ADR-0010 的主键/公开编码、既有项目 ACL、共享版本与不可变证据规则。

## 已接受的决定

1. **客户与身份**：建立独立 tenant；一个客户可以有多个 team。保留全局登录账号，用户通过明确邀请加入一个或多个客户，每次业务请求验证活动客户。客户成员角色与 team/project 角色分层，客户目录不能因此暴露全局人员。
2. **跨客户技能交付**：允许显式、逐已发布版本、经接收方确认的跨客户技能授权。源发布与目标接收分别记录；共享技能不自动开放源客户的项目、成员、草稿、其它版本或其它私有内容。不默认为公共技能市场。旧共享和已冻结交付证据必须有可核实迁移计划，不静默撤销、删除或虚构接收确认。
3. **平台支持权限**：平台日常操作限元数据运维；客户正文访问需要限定客户、限定时长、附原因的支持授权并写审计。客户管理员与平台 `is_system_admin` 分离；平台应用身份不对应数据库 superuser、owner 或 BYPASSRLS。正文 API、SQL、附件、导出与缓存都不能绕过支持授权边界。

## 后续实现约束

- 按评估第 11 节的小批次推进。先完成客户归属盘点、最小数据库角色、可信上下文和事务接线，再启用对应聚合的 RLS；不能对当前 team_id 直接套客户 policy。
- 保留应用 ACL、Owner/Admin/Viewer、草稿与归档规则、乐观并发、审计和双平面边界。RLS 提供数据库客户行边界，不取代业务鉴权。
- 租户资源采用显式客户归属与必要的复合 FK；身份/认证控制面、技能授权桥、混合审计分别设计，不使用 `tenant_id IS NULL` 或管理员请求头作为通用放行规则。
- 普通应用角色不拥有表、不继承 owner、不具有 BYPASSRLS；客户上下文需可信、事务局部且绑定真实连接。仅能被任意 SQL 覆盖的 tenant/principal GUC 不构成身份验证。
- 迁移分展开、回填/双写验证、受控切换与收缩；只有实际角色、原生 SQL、池复用、跨客户分享、后台任务与恢复矩阵通过后，才能声明相应隔离范围已交付。

## 理由与影响

当前用户、团队和项目模型允许多团队与团队外显式授权，技能已具备版本级共享；将每个 team 当成独立客户会改变这些语义。新增客户边界既要限制私有信息，也要让明确获授的交付继续成立。平台客户管理与平台全局运营的权责不同，不能通过统一管理员位替代。

本 ADR 接受后，不再把这三项列为待用户决定。具体逐记录客户映射、技术安全机制与小批次实施仍需代码/数据评审；这不是重新讨论已确定的产品方向。未来改变上述边界须新增 ADR 取代本记录，不静默修改其 Accepted 含义。
